# Entertainment motion validation

## User quality rejection and redesign

The user rejected all three entertainment outputs below as poor quality. They remain rejected experiments; legibility fixes and technical passes did not establish sufficient visual craft. The subsequent work revisits assets, shot scale, composition, typography and purposeful action rather than treating the rejection as a request for smaller cosmetic corrections.

The active plugin paths now include `frameforge-motion/visual-development`, exposed through `read_skill` and referenced by the MCP motion prompt, maker and make command. It asks the maker to build and inspect a representative shot before extending the timeline. The old shape-count, palette-count, medium and mandatory-motion prescriptions are no longer universal creative rules. This change addresses a documented conflict in the guidance; it does not prove that those rules alone caused the rejected results or that changing prompts automatically improves future films.

Three separate creator agents were requested with `gpt-6-astra` and high reasoning effort for the redesign. This records the accepted tool configuration, not an independently exposed runtime model ID. They read the updated visual-development guidance and revised actual rendered shots with parent and independent feedback. These are guided collaboration runs, not an isolated test of automatic plugin discovery in a fresh Codex app session.

The redesigned game work compared static official [LINE studio promotional imagery](https://linestudio.com/) with its own saved output. The music work additionally inspected [Studio Moross music visuals](https://www.studiomoross.com/project-categories/live-visuals), and [Seventeen's Viasat Kino identity](https://www.seventeenagency.com/project/viasat-kino) as a composition reference; the latter is a cinema identity, not a music promotion. Reference images were not incorporated into the films. These observations do not establish reference-motion rhythm or audio quality.

## Renderer cancellation found during this work

A prior whole-suite run recorded 310 passes and three failures: two Chrome DevTools connection closures and one `fetch failed` response. Concurrent film rendering and later host disconnection were observed, but neither resource contention nor the cancellation defect below is established as the cause of those three failures.

A separate, concrete defect was reproduced: the previous snapshot CLI's SIGTERM handler exited before its page cleanup, so signalling only the renderer could leave its real Chrome child alive. An isolated baseline failed the new direct-signal test after waiting five seconds for Chrome to exit. The revised renderer tracks its launched browsers and attempts to terminate them before exiting; the direct-signal and ordinary MCP cancellation cases both passed. The ordinary MCP case also passed on the baseline, so it is not claimed as a deterministic reproduction of the leak. Tests confirm the owned Chrome PID and snapshot copy are gone, and that an unrelated process-group sentinel survives. They do not establish complete cleanup of every Chrome helper, separate session or ordinary render temporary directory.

The final isolated release run on base `1bd89b6c22a624879868b44c5fd7c5997bbceea9` plus this change passed all **314 tests**, with zero failures or skips. The count increased from 313 because of the direct-SIGTERM regression. This passing rerun does not establish the cause of the earlier three transient failures. TypeScript, production build, MCP skill discovery/readback and plugin validation also passed; the plugin validator retained existing directory/context warnings. Each redesigned film passed its own determinism lint. The compatibility benchmark matched all 1,554 cases. A separate 30-frame moving-shape fixture rendered with the baseline and revised renderer had 30 identical decoded frames (PSNR infinity), confirming unchanged normal output for that fixture. The first benchmark attempt was blocked by the sandbox IPC restriction; the authorized local run passed.

## Reference scope

The public LINE GAME promotional materials were reviewed as visual and information-design references, not as assets to reproduce. The [LINE Bubble 2 event page](https://linegame-official.blog.jp/archives/63437100.html) shows a large central character with smaller supporting characters; its text connects daily missions with tickets and stage completion with rewards. The [LINE Pokopoko event page](https://linegame-official.blog.jp/archives/63163802.html) uses prominent outlined headings and expressive characters, while its reward banner separates the reward from its conditions and deadline. These observations are from still images and page text. The [official 15-second promotion](https://www.youtube.com/watch?v=XRfgW55q_gk) was identified, but video playback did not load, so its motion, transitions and rhythm were not observed.

The independent game film uses its own fictional character, event and graphics; it does not use LINE logos or character assets. The transferable design question is whether the viewer can identify the character, goal, reward and condition, not whether a particular branded layout is copied.

## Limits

These are local experiments, not a benchmark across models or proof of professional-quality equivalence. Neither production was inspected through actual normal-speed playback or direct listening; the stills, mobile-size downsampling and waveform measurements do not establish perceived rhythm, phone-screen legibility, audio quality or sync. The films were produced through collaboration agents, not a verified fresh Codex app session. Model identity for the game and music production was not exposed to those agents. Existing global Frameforge skills pointed to a separate checkout, so this work does not prove that the latest plugin is installed or automatically loaded in a new Codex session. Artifacts remain local and are identified by hashes above.

An independently prompted collaboration agent also created the same factual football brief without seeing prior output. It actually called the current MCP `make_motion_film` prompt, `read_skill`, and `film_new`, and produced a local MP4 (SHA-256 `585507a6d65d110611005bc83f4a7d8e82caad9238fe5ba8e566f508ad1f82e8`). A separate saved-frame review found correct sampled score states but repeated the same scoreboard composition for all three goals and replaced it with a separate result card. This shows that exposing the workflow is not proof that an agent will produce reference-level continuity. It was not an independent Codex app session.

For the earlier v10 football revision, downsampled 360-pixel stills retained the goal times; at 270 pixels the times were very small. Local v11 (SHA-256 `5aab1eefc93000c4c0dba86860059b0353552f9609ceee728ee9294ed0e020f3`) enlarges the time text and nodes. An independent comparison of saved MP4 frames at 270×480 found the times easier to distinguish with the sampled totals intact. Closer node spacing is a tradeoff, and device playback remains unverified.
