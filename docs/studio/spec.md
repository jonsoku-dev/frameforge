# Frameforge 스튜디오 2.0 사양

작성 2026-10-20. 대상은 `src/studio/`와 `vite.config.ts`의 개발 서버 미들웨어다. 이 문서는 사양이다. 구현은 `src/studio/`와 `vite.config.ts`에 있고, 아직 구현하지 않은 항목은 본문에 2.1, 나중, 미구현으로 표시한다.

## 0. 2.0 이전에 스튜디오가 못 하던 것

2.0 이전의 `src/studio/main.tsx`는 장면 목록, 재생, 시간 슬라이더, 글자 잘림 표시, "영상 저장" 버튼 하나였다. 지금 `main.tsx`는 부팅과 렌더 모드 다리만 맡고 화면은 `App.tsx`가 그린다. 사용자가 실제로 하는 일은 다른 곳에서 일어난다. 기획은 `prompt.md`, 소리는 `audio.json`, 리뷰는 리뷰 파일, 수정 내역은 `docs/samples/README.md`의 "리뷰가 찾은 것 / 고친 것", 검사 결과는 `renders/samples/results.json`, 시트는 `renders/samples/*-sheet.png`에 흩어져 있다. 옛 스튜디오는 이 중 하나도 보여 주지 않았다. 장면 이름과 모델 표기는 `main.tsx` 안의 `SCENE_TITLES` 표에 손으로 적혀 있었다. 값 하나를 바꾸려면 `Spot.tsx`를 열어야 했고, 렌더는 진행률 없이 수십 초 동안 "저장하고 있습니다"만 보였다.

2.0은 이 흩어진 기록을 컴포지션 폴더 하나로 모으고, 스튜디오를 그 폴더의 작업대로 만든다. 로컬 도구로 남는다. `npm run dev`로 서버를 켜고 `http://127.0.0.1:4317`을 연다.

용어는 다음처럼 고정한다.

| 용어 | 뜻 |
| --- | --- |
| 컴포지션 | `<Composition id="...">` 하나. 예 `KitLaunch` |
| 폴더 | 컴포지션의 원본 폴더. 예 `examples/samples/kit-launch/` |
| 기획서 | 폴더의 `prompt.md` |
| 실행(run) | 작성, 리뷰, 수정, 렌더, 검사, 캡처, 요청 중 하나의 기록. `process.json`에 쌓인다 |
| 버전 | `author` 또는 `fix` 실행이 만든 상태. v1, v2처럼 부른다 |
| 변수 | 컴포지션이 선언한 조정 가능한 값 |
| 덮어쓰기 | 변수의 기본값 대신 쓰는 값. 폴더의 `overrides.json` |
| 산출물 | 실행이 남긴 파일. 시트, MP4, 스틸, 리뷰 문서, 로그 |

## 1. 사용자와 작업 흐름

세 사람은 한 사람일 수도 있다. 역할로 나눈 것은 각 역할이 스튜디오에서 먼저 찾는 것이 다르기 때문이다.

### 1.1 기획자

영상의 목적, 장면표, 색과 글꼴, 소리를 `prompt.md`와 `audio.json`으로 쓰고 에이전트에게 맡긴다. 스튜디오를 여는 이유는 "내 기획서대로 나왔는가"와 "에이전트가 어디까지 했는가"를 보는 것이다.

| 일 | 빈도 | 스튜디오에서 하는 동작 |
| --- | --- | --- |
| 에이전트 작업 상태 확인 | 하루 여러 번 | 레일에서 컴포지션 고르고 과정 탭의 최근 실행 읽기 |
| 기획서 장면표와 실제 화면 대조 | 작품마다 2–3회 | 타임라인 장면 띠를 눌러 그 장면으로 이동, 기획 탭과 무대를 나란히 보기 |
| 변경 요청 남기기 | 작품마다 3–10회 | 문제 프레임에서 C, 요청 문장 쓰고 ⌘Enter |
| 어떤 모델이 무엇을 했는지 비교 | 주 1회 | 과정 탭에서 실행 주체와 요약 읽기 |
| 새 작품 시작 | 주 1–2회 | 스튜디오 밖에서 폴더와 기획서를 만든다. 스튜디오는 빈 상태로 그 폴더를 보여 준다 |

### 1.2 검수자

정지 화면을 프레임 단위로 본다. 2.0 이전에는 시트 PNG를 열어 보고 타일이 몇 번 프레임인지 기획서의 "검사 프레임" 목록과 손으로 맞췄다. 시트 타일에 프레임 번호가 없기 때문이다(열 장짜리 시트는 타일에 번호가 없고, 기획서의 검사 프레임은 16개라서 시트만으로는 어느 프레임인지 알 수 없다).

| 일 | 빈도 | 스튜디오에서 하는 동작 |
| --- | --- | --- |
| 시트 타일을 프레임으로 찾아가기 | 작품마다 10–20회 | 타임라인 과정 레인의 시트 눈금을 눌러 그 프레임으로 이동 |
| 한 프레임씩 넘기며 보기 | 작품마다 수백 번 | ←/→, Shift+←/→ |
| 글자 잘림, 세이프 영역 확인 | 장면마다 | G로 세이프 영역 표시, 무대 위 잘림 칩 |
| 리뷰 지적과 수정이 맞는지 확인 | 리뷰마다 | 과정 탭에서 리뷰 실행의 지적을 열고, 이를 해결한 수정 실행으로 이동 |
| 지적을 남기기 | 작품마다 5–10회 | C로 변경 요청. 2.1부터는 프레임 구간 지적 |

### 1.3 마무리 담당

변수를 조정하고, 렌더하고, 검사를 통과시켜 내보낸다.

| 일 | 빈도 | 스튜디오에서 하는 동작 |
| --- | --- | --- |
| 문구, 색, 타이밍, 음량 미세 조정 | 작품마다 10–30회 | 조정 탭에서 값 바꾸고 무대에서 즉시 확인, ⌘S로 저장 |
| 시트 렌더로 빠르게 확인 | 조정 묶음마다 | 출력 탭에서 시트 만들기. 기획서 검사 프레임이 미리 채워져 있다 |
| MP4 렌더와 검사 | 작품마다 2–5회 | 출력 탭 MP4 만들기, 진행률 보기, 결과 카드의 검사 다섯 줄 확인 |
| 실패한 검사 고치기 | 실패마다 | 결과 카드의 실패 줄에서 해당 프레임이나 변수로 이동 |
| 소스 열기 | 하루 여러 번 | 무대 머리줄의 "에디터에서 열기" |

### 1.4 핵심 흐름

```
기획자                 에이전트                     스튜디오                       마무리 담당
prompt.md, audio.json ─▶ author 실행 (v1) ─────────▶ 과정 탭에 v1, 시트 눈금 ─────▶
                         review 실행 (지적 n개) ───▶ 지적 목록
                         fix 실행 (v2, 해결 목록) ─▶ "바뀐 것" 문장
검수자 ◀──────────────────────────────────────────── 시트 눈금 ↔ 무대 프레임
검수자 C (요청) ─────────▶ request 실행 ──▶ 에이전트가 읽고 fix 실행으로 해결
                                                     조정 탭 → overrides.json ◀──── 값 조정, ⌘S
                                                     출력 탭 → render, check 실행 ◀ MP4 렌더
```

### 2.2 크기 규칙

| 창 폭 | 레일 | 검사기 | 타임라인 높이 | 레인 높이 |
| --- | --- | --- | --- | --- |
| 1600 px 이상 | 248 px, 펼침 | 400 px | 208 px | 24 px |
| 1280–1599 px | 64 px, 접힘. `\` 키나 레일 머리의 펼침 버튼으로 무대 위에 겹쳐 펼침 | 360 px | 176 px | 20 px |
| 1024–1279 px | 접힘 | 무대 위 오른쪽 서랍, `I`로 열고 닫음 | 176 px | 20 px |
| 1024 px 미만 | 지원하지 않음. 무대와 타임라인만 보이고 위 막대에 "1024 px 이상에서 모든 패널이 보입니다"를 띄운다 | | | |

무대는 남는 공간 전부다. 컴포지션은 비율을 지켜 맞춤으로 들어가고 가운데 정렬된다. 계산 예. 1280×700 창에서 무대 영역은 폭 1280 − 64 − 360 = 856 px, 높이 700 − 44 − 36 − 176 = 444 px. 16:9 컴포지션은 높이가 먼저 차서 789×444 px다. 1920×960 창에서는 폭 1272, 높이 960 − 44 − 36 − 208 = 672 px라서 1195×672 px다. 9:16 컴포지션은 1280 창에서 250×444 px로 작다. 그래서 무대 머리줄에 "맞춤 / 100%" 전환을 두고, 100%에서는 무대가 스크롤된다. 페이지 전체는 어느 폭에서도 가로 스크롤이 생기지 않는다.

### 2.3 위 막대

| 요소 | 내용 |
| --- | --- |
| 로고 | `Clapperboard` 아이콘과 "frameforge" |
| 진입 파일 | 지금 `VIDEO_ENTRY`. 고정 폭 글꼴 12 px, 눌러 경로 복사 |
| 연결 상태 | "연결됨"(초록 점), "다시 연결하는 중"(노랑), "서버 꺼짐"(빨강). Vite HMR 소켓 상태를 그대로 쓴다. 소켓이 끊기면 "다시 연결하는 중"이고 10초 안에 돌아오지 않으면 "서버 꺼짐"이다 |
| 렌더 표시 | 진행 중인 작업이 있으면 "렌더 412/900"과 가는 진행 막대. 누르면 그 컴포지션의 출력 탭 |
| 도움말 | `?` 버튼. 단축키 표를 연다 |

### 2.4 프로젝트 레일

컴포지션마다 한 줄. 위에서 아래로 진입 파일에 등록된 순서다.

| 요소 | 펼침(248 px) | 접힘(64 px) |
| --- | --- | --- |
| 썸네일 | 가장 최근 시트의 첫 타일을 잘라 48×27(가로) 또는 27×48(세로) | 같음 |
| 제목 | `prompt.md`의 첫 `#` 제목. 없으면 컴포지션 ID | 툴팁 |
| 형식 | "16:9 · 30초" 또는 "9:16 · 15초" | 없음 |
| 작성 주체와 버전 | 첫 `author` 실행의 actor와 현재 버전. 예 "opus · v3" | 없음 |
| 검사 점 | 최신 검사가 모두 통과면 초록, 하나라도 실패면 빨강, 결과가 지금 버전보다 오래되었으면 회색 테두리, 결과 없음이면 빈 원 | 같음 |
| 열린 요청 수 | 해결되지 않은 `request` 실행 수. 0이면 숨김 | 점 옆 숫자 |
| 저장 안 됨 | 조정 탭에 저장하지 않은 변경이 있으면 제목 옆 작은 점 | 썸네일 모서리 점 |
| 렌더 중 | 줄 아래 2 px 진행 막대 | 같음 |

레일 머리에는 컴포지션 수와 접기 버튼이 있다. 필터 입력은 2.1이다.

`SCENE_TITLES` 표는 지운다. 제목은 기획서에서, 모델은 과정 기록에서 온다.

### 2.5 무대

무대 머리줄(36 px)과 무대 본체로 나뉜다.

무대 머리줄 왼쪽은 제목, 형식, 현재 버전 배지다. 가운데는 현재 프레임 "410 / 899"와 시간 "0:13:20"이다(2.9절 끝의 시간 형식). 오른쪽에는 다음 컨트롤이 있다.

- 안전 영역 토글(G). 5장 참조.
- 글자 잘림 칩. "잘림 0"은 회색, "잘림 2"는 빨강. 누르면 잘린 글자, 방향, 픽셀 목록이 뜬다.
- 맞춤 / 100% 전환.
- 에디터에서 열기 분할 버튼. 기본 동작은 `Spot.tsx`, 펼치면 `prompt.md`, `audio.json`, `process.json`, `overrides.json`.
- 반영 시간. 조정 탭에서 값을 바꾼 뒤 무대가 다시 그려지기까지의 밀리초. "반영 37 ms"처럼 4장의 100 ms 규칙을 눈으로 확인하게 한다. 마지막 변경 후 3초 동안만 보인다.

무대 본체는 컴포지션을 맞춤 크기로 그린다. 바탕은 중립 회색(6장 `--stage`)이고 프레임 가장자리에 1 px 테두리를 둔다. 컴포지션 배경이 검정이든 흰색이든 프레임 끝이 보이게 하기 위해서다. 지금의 `Stage` 컴포넌트, 잘린 글자 빨간 테두리, `Boundary` 오류 표시는 그대로 쓴다.

### 2.6 검사기

탭 넷. 숫자 키 1–4로 바꾼다.

| 탭 | 용도 | 주 사용자 |
| --- | --- | --- |
| 기획 | `prompt.md`와 `audio.json` 읽기 | 기획자, 검수자 |
| 과정 | 실행 기록, 버전, 리뷰 지적, 변경 요청 작성 | 기획자, 검수자 |
| 조정 | 변수 값 조정, 덮어쓰기 저장 | 마무리 담당 |
| 출력 | MP4와 시트 렌더, 진행률, 결과와 검사 | 마무리 담당 |

검사 결과를 따로 탭으로 두지 않는다. 결과는 렌더 산출물에 붙어 있으므로 출력 탭의 결과 카드에 있고, 실패는 레일 점, 무대 칩, 타임라인 검사 레인에도 동시에 보인다.

#### 기획 탭

```
┌ 기획 ──────────────────────────────┐
│ prompt.md            [에디터에서 ↗] │
│ ─────────────────────────────────  │
│ # kit-launch                        │
│ **목적.** 할 일에 묻힌 사람에게 ...  │
│ ## 장면표                           │
│ | 프레임 | 화면을 채우는 것 | ...    │
│   (원문 그대로, 줄바꿈 유지)         │
│ ─────────────────────────────────  │
│ 소리  audio.json     [에디터에서 ↗] │
│ upbeat · 120 bpm · C major · seed 10│
│ 구간 problem 0–5s 0.25              │
│      pin 5–8.3s 0.5 ...             │
│ 히트 5s, 22s                        │
│ 음량 목표 −24 LKFS, TP −2 dBTP      │
│ 효과음 whoosh, click                │
└────────────────────────────────────┘
```

2.0은 `prompt.md`를 원문 그대로 보여 준다(줄바꿈 유지, UI 글꼴 13 px). 마크다운 렌더링은 2.1이다. 장면표 행에 마우스를 올리면 해당 장면 띠가 타임라인에서 밝아지는 연결도 2.1이다. `audio.json`은 해석해서 위처럼 요약한다. 히트는 숫자이거나 `{at, weight, style}` 객체인데 `src/studio/model.ts`가 객체는 `at`만 읽어 초로 보여 주므로 `weight`와 `style`은 보이지 않는다. 효과음은 `sfx` 항목의 이름만 나열하고 `preset` 같은 나머지 필드는 보이지 않는다.

| 저장 안 된 변경 | 조정 탭, 레일 | 아래 막대 "저장 안 된 변경 N", 레일 점. 다른 컴포지션으로 가도 묻지 않는다. 초안은 브라우저에 남는다 |

| 소리 재생 거부 | 전송 줄 | 브라우저 자동 재생 차단 시 음소거 아이콘에 "눌러서 소리 켜기" |

### 2.9 단축키

입력칸, 텍스트 영역, 선택 상자에 초점이 있으면 전역 단축키는 꺼진다. 예외는 ⌘S, ⌘Enter, Esc다. `App.tsx`의 `typing` 검사가 이를 막는다. 입력칸, 텍스트 영역, 선택 상자, `contenteditable`, `role="slider"`가 대상이다.

| 키 | 동작 |
| --- | --- |
| Space | 재생, 일시정지. 끝에서 누르면 처음부터 |
| ← / → | 1프레임 |
| Shift + ← / → | 10프레임 |
| Home / End | 처음, 마지막 프레임 |
| [ / ] | 이전, 다음 장면 시작(장면 레인 기준) |
| , / . | 선택한 실행의 이전, 다음 시트 프레임 |
| ↑ / ↓ (레일에 초점) | 이전, 다음 컴포지션 |
| 1 / 2 / 3 / 4 | 검사기 탭 기획, 과정, 조정, 출력 |
| I | 검사기 열고 닫기(1280 px 미만에서는 서랍) |
| \ | 레일 접고 펼치기 |
| G | 안전 영역 표시 |
| F | 맞춤과 100% 전환 |
| C | 현재 프레임으로 변경 요청 작성기에 초점 |
| E | `Spot.tsx`를 에디터에서 열기 |
| R | 출력 탭으로 가서 MP4 만들기 버튼에 초점(바로 시작하지 않는다) |
| ⌘S | 조정 덮어쓰기 저장 |
| ⌘Enter | 변경 요청 보내기 |
| Esc | 팝오버, 서랍 닫기. 입력칸에서 초점 빼기 |
| ? | 단축키 표 |

레일 접기가 `[`가 아니라 `\`인 이유는 `[`와 `]`를 장면 이동에 쓰기 때문이다.

시간 표시는 `분:초:프레임`이다. 30 fps에서 프레임 410은 13초 20프레임이므로 `0:13:20`이다. 프레임 단위로 일하는 도구라서 소수 초 대신 프레임을 보인다.

### 2.10 URL과 새로고침

선택한 컴포지션과 프레임을 주소의 해시에 둔다. 예 `#/KitLaunch@410`. 에이전트가 `Spot.tsx`를 고치면 Vite가 페이지를 다시 불러오는데, 해시 덕분에 같은 컴포지션의 같은 프레임으로 돌아온다. 검사기 탭과 레일 접힘 상태는 `localStorage`에 둔다. 처음 열 때 탭은 과정이다. 에디터 선택은 `frameforge:editor`, 초안은 `frameforge:draft:<컴포지션 ID>`에 둔다.

## 3. 프로세스 가시성

### 3.1 파일 위치

컴포지션 폴더마다 `process.json` 하나. 예 `examples/samples/kit-launch/process.json`. 커밋 대상이다. 생성된 오디오처럼 다시 만들 수 있는 것이 아니기 때문이다.

### 3.2 계약

사용자가 정한 모양을 기준으로 하고, 다음을 더했다. 실행 `id`, `kind`의 `request`, 산출물의 `frames`, 선택 필드 `frame`, `changes`, `findings`, `resolves`. 더한 이유는 각 필드 설명에 있다. 아래 예는 기록의 모양을 보이는 예다. 지금 `process.json`이 있는 샘플은 없다. 리뷰의 지적 다섯 중 둘만 적었다.

```json
  "brief": "prompt.md",
  "audio": "audio.json",
  "runs": [
    {
      "id": "r01",
      "at": "2026-10-18T09:12:00+09:00",
      "actor": "claude opus",
      "kind": "author",
      "prompt": {"path": ".scratch/samples/brief-kit-launch.md"},
```

| `frame` | 정수 또는 없음 | `request`와 `capture`에서 가리키는 프레임. `request`는 "프레임 없음"이면 뺀다 |
| `changes` | 문자열 배열 또는 없음 | `fix`에서 "바뀐 것" 줄. 코드 차이가 아니라 사람이 읽는 문장 |
| `findings` | 배열 또는 없음 | `review`에서 지적 목록. 각 `{id, from?, to?, text}`. `id`를 빼면 `append`가 `<실행 id>-1`부터 붙인다. `from`이 있으면 지적을 눌러 그 프레임으로 간다. 지적을 타임라인에 구간으로 놓는 것은 2.1이다(미구현) |
| `resolves` | 문자열 배열 또는 없음 | `fix`가 해결한 지적 id나 요청 실행 id |

`kind`별 필수 필드는 다음과 같다.

| kind | 필수 | 보통 함께 |
| --- | --- | --- |
| author | summary | prompt, sheet 산출물 |
| review | summary | review 산출물, findings |
| fix | summary | changes, resolves, sheet 산출물 |
| render | summary, mp4 또는 sheet 산출물 | metrics.seconds, metrics.overrides |
| check | summary, metrics.of | log 산출물 |
| capture | summary, still 산출물 | frame |
| request | summary, prompt.text | frame, still 산출물(2.1) |

### 3.3 버전

버전 번호는 저장하지 않고 계산한다. `runs`를 처음부터 읽으며 `author` 또는 `fix`를 만날 때마다 1씩 올린다. 첫 `author`가 v1이다. 다른 실행은 그 시점의 버전에 속한다. 렌더 실행이 v3에 속하면 그 결과는 "v3 결과"다. 저장하지 않는 이유는 숫자를 두 곳에 두면 언젠가 어긋나기 때문이다.

조정 탭의 저장도 `fix` 실행을 만든다(actor `human`). 그래서 값만 바꿔도 버전이 오른다.

버전마다 보이는 "바뀐 것"은 `changes` 배열이다. 없으면 `summary`를 쓴다. 코드 차이는 보여 주지 않는다. 이 프로젝트는 git 저장소가 아니고, 실행이 소스 스냅숏을 남기지도 않는다. 그래서 2.0은 옛 버전으로 되돌릴 수 없다. 옛 버전의 시트와 MP4는 산출물로 남아 있으니 볼 수는 있다. 되돌리기는 실행이 `Spot.tsx`와 `overrides.json` 사본을 남기는 "스냅숏" 기능이 생긴 뒤의 일이다(나중).

렌더 산출물이 버전마다 남는 이유는 `renderMedia`가 이미 있는 출력 경로에 쓰지 않고 오류를 내기 때문이다. 스튜디오 렌더는 언제나 새 경로 `renders/studio/<slug>/<YYYYMMDD-HHMMSS>-v<N>.<mp4|png>`에 쓴다. 덮어쓰기가 없으니 이전 결과가 그대로 실행 기록이 된다.

### 3.4 실행 카드

| kind | 아이콘(lucide) | 머리줄 | 본문 | 동작 |
| --- | --- | --- | --- | --- |
| author | `PenLine` | actor · 날짜 · 버전 배지 | summary | 프롬프트 보기, 시트 열기 |
| review | `Flag` | actor · 날짜 · "지적 N개" | summary, 지적 목록. 각 지적 옆에 해결한 버전("✓ v2") 또는 "미해결" | 리뷰 문서 열기, 지적 누르면 그 구간 시작 프레임으로 이동 |
| fix | `Wrench` | actor · 날짜 · 버전 배지 | "바뀐 것" 줄, "해결한 지적 N개 (리뷰 actor)" | 프롬프트 보기, 시트 열기 |
| render | `Film` 또는 `LayoutGrid` | script · 날짜 · 소속 버전 | "MP4 77초 · 900프레임" 또는 "시트 16장" | 재생, 시트 열기, 경로 복사 |
| check | `ShieldCheck` / `ShieldAlert` | script · 날짜 | 검사 넷의 통과, 실패, 기록 없음을 한 줄로 | 출력 탭 결과 카드로 이동 |
| capture | `Camera` | actor · 날짜 · 프레임 | summary, 스틸 썸네일 | 그 프레임으로 이동 |
| request | `MessageSquarePlus` | actor · 날짜 · 프레임 · "열림"/"해결 v4" | 요청 문장 | 그 프레임으로 이동 |

공통 규칙.

- 날짜는 오늘이면 "3분 전", 그 밖은 "10-19 14:30". 마우스를 올리면 ISO 시각 전체.
- "프롬프트 보기"는 `prompt.text`를 카드 안에 펼치거나 `prompt.path` 파일을 검사기 위 읽기 서랍에 연다(`GET /api/file`).
- 시트 산출물은 썸네일 한 줄(타일 4장)과 "▦ 16장". 누르면 시트 보기(3.6절).
- MP4는 "재생"으로 검사기 위 서랍에서 `<video>`로 재생한다(`GET /api/media`).
- 리뷰 문서는 읽기 서랍에 원문으로 연다.
- 요청이 "열림"인지 "해결"인지는 계산한다. 뒤에 오는 어떤 `fix`의 `resolves`에 그 요청 id가 있으면 해결이다. 지적도 같다. 요청에 상태 필드를 두고 고쳐 쓰지 않는다. 기록은 덧붙이기만 하기 때문이다.
- 실행 카드를 누르면 "선택한 실행"이 된다. 타임라인 과정 레인은 선택한 실행의 산출물 프레임을 보여 준다. 아무것도 선택하지 않으면 가장 최근 시트를 가진 실행이 기본이다.

### 3.5 정지 화면을 타임라인에 놓기

시트와 스틸 산출물의 `frames`를 과정 레인에 세로 눈금으로 찍는다. 눈금 위에 마우스를 올리면 그 타일을 잘라 160 px 폭 미리보기로 띄우고, 누르면 그 프레임으로 이동한다. `,`와 `.`로 눈금 사이를 오간다.

타일 위치는 `scripts/render.mjs`의 FFmpeg 필터에서 나온다. `scale=480:-1,tile=<열>x<행>:padding=4:color=white`이고 열 수는 `min(4, 프레임 수)`다. 그래서 i번째 타일(0부터)은 다음 자리에 있다.

| 값 | 식 |
| --- | --- |
| 타일 폭 | 480 |
| 타일 높이 | `round(480 × 높이 / 폭)`. 1920×1080이면 270, 1080×1920이면 853 |
| 열 | `i mod 열 수` |
| 행 | `floor(i / 열 수)` |
| x | `열 × (480 + 4)` |
| y | `행 × (타일 높이 + 4)` |

열 장짜리 시트는 1932×818 px, 4열 3행이다. 4 × 480 + 3 × 4 = 1932, 3 × 270 + 2 × 4 = 818이라서 이 식과 맞는다. 바깥 여백은 없고 타일 사이에만 4 px가 있다. 렌더러가 이 식을 바꾸면 스튜디오의 잘라내기도 같이 바꿔야 하므로, 2.1에서 `render.mjs`가 시트 옆에 `<시트>.json`(`frames`, `columns`, `tileWidth`, `tileHeight`, `padding`)을 쓰고 스튜디오는 그 파일이 있으면 그것을 읽는다. 이 사이드카 파일은 아직 구현하지 않았고, 지금 스튜디오는 위 식으로 자른다.

### 3.6 시트 보기

시트 산출물을 열면 검사기 위 서랍에 시트를 띄우고, 각 타일 왼쪽 위에 프레임 번호 배지를 겹친다(PNG에는 없으므로). 타일을 누르면 서랍이 닫히고 무대가 그 프레임으로 간다. 2.1에서는 "비교"가 생긴다. 무대에 옛 스틸과 현재 라이브 프레임을 반반 나누어 보여 주고, 가운데 손잡이를 끌어 경계를 옮긴다. 검수자가 "고쳐졌는가"를 한 화면에서 판단하게 하는 기능이다.

### 3.7 누가 기록하나

| 기록 | 쓰는 쪽 | 2.0 | 2.1 |
| --- | --- | --- | --- |
| render, check | 스튜디오 서버의 렌더 작업 | 있음 | CLI `render.mjs`도 폴더에 `process.json`이 있으면 기록 |
| fix(사람, 덮어쓰기 저장) | 스튜디오 서버 | 있음 | |
| request | 스튜디오 서버 | 있음 | |
| author, review, fix(에이전트), capture | 에이전트 | 덧붙이기 도우미의 CLI로 | 같음 |

쓰기 규칙은 하나다. 모든 쓰기는 `scripts/process.mjs`의 덧붙이기 함수를 거친다. 서버도 이 함수를 가져다 쓰고, 에이전트는 같은 파일의 CLI를 부른다. 예 `node scripts/process.mjs append examples/samples/kit-launch '{"actor":"claude opus","kind":"fix","summary":"...","changes":["..."],"resolves":["r06"]}'`. 나머지 명령은 `init <폴더>`와 `validate <폴더>`다. `--actor`, `--kind` 같은 플래그 형식은 없고 실행은 JSON 한 덩어리로 받는다. 이 함수는 다음을 한다.

1. `process.json.lock`을 배타적으로 만든다. 이미 있으면 50 ms 간격으로 최대 2초 기다린 뒤 실패한다. 10초보다 오래된 잠금 파일은 죽은 것으로 보고 지운다.
2. 파일을 읽고 3.2절 규칙으로 검사한다. 파일이 없으면 `{brief: 'prompt.md', audio: 폴더에 audio.json이 있으면 'audio.json', runs: []}`로 시작한다.
3. 새 `id`를 붙이고(`at`이 없으면 지금 시각, `findings`의 `id`가 없으면 `<실행 id>-<번호>`) 실행을 검사한 뒤 덧붙인다.
4. 같은 폴더의 임시 파일에 쓰고 이름을 바꿔 원자적으로 교체한다.
5. 잠금 파일을 지운다.

에이전트가 JSON을 손으로 고치게 두지 않는 이유는 쉼표 하나가 과정 탭 전체를 깨뜨리기 때문이다.

### 3.8 에이전트 규약

에이전트에게 주는 브리프(예 `.scratch/samples/brief-common.md`)에 다음 문단을 넣는다.

> 작업을 시작하기 전에 폴더의 `process.json`을 읽는다. `kind`가 `request`이고 어떤 `fix`의 `resolves`에도 들어 있지 않은 실행이 열린 요청이다. 열린 요청을 처리했으면 `node scripts/process.mjs append <폴더> '<실행 JSON>'`으로 `kind`가 `fix`인 실행을 남기고 `changes`(사람이 읽는 문장)와 `resolves`(처리한 요청 id)를 채운다. 시트를 찍었으면 `artifacts`에 `{"kind":"sheet","path":"...","frames":[...]}`를 넣는다. `overrides.json`의 값은 사용자가 정한 것이다. 소스 기본값을 그 값으로 바꾸라는 요청이 없으면 덮어쓰기를 지우지 않는다.

## 4. 세부 개선(튜닝)

### 4.1 변수 선언 계약

컴포지션 폴더의 `Spot.tsx` 옆에서 `export const variables`로 배열을 내보낸다. 각 항목의 필드는 다음과 같다.

| 필드 | 형식 | 모든 타입 | 설명 |
| --- | --- | --- | --- |
| `key` | 문자열, 영문 camelCase | 필수 | 컴포넌트가 받는 prop 이름. 컴포지션 안에서 유일 |
| `type` | `string`, `color`, `number`, `enum`, `boolean`, `audioVolume` | 필수 | |
| `label` | 문자열 | 필수 | 조정 탭에 보이는 한국어 이름 |
| `default` | 타입에 맞는 값 | 필수 | 소스의 기본값. 덮어쓰기가 없으면 이 값 |
| `group` | 문자열 | 선택 | 조정 탭의 묶음 제목. 예 "문구", "색", "타이밍", "소리" |
| `preview` | 정수 | 선택 | 이 변수 입력칸에 초점이 가면 무대가 이 프레임으로 간다. 헤드라인 변수라면 헤드라인이 다 보이는 프레임 |
| `help` | 문자열 | 선택 | 입력칸 아래 한 줄 설명 |

| type | 추가 필드 | 값 | 컨트롤 |
| --- | --- | --- | --- |
| `string` | `maxLength?`(기본 120), `multiline?` | 문자열 | 한 줄 입력칸, `multiline`이면 텍스트 영역 |
| `color` | 없음 | `#RRGGBB` 대문자 | 색 견본(네이티브 색 선택기)과 16진 입력칸 |
| `number` | `min`, `max`, `step` 필수. `unit?`은 `frames`, `px`, `%`, `x` 중 하나 | 숫자 | 슬라이더와 숫자 입력칸. `unit`이 `frames`이면 "−6 프레임 (−0.20초)"처럼 초도 보인다 |
| `enum` | `options: [{value, label}]` 2개 이상(6개까지 권장) | `value` 중 하나 | 3개 이하면 분할 버튼, 넘으면 선택 상자 |
| `boolean` | 없음 | 참, 거짓 | 체크 상자 |
| `audioVolume` | 없음. 범위 0–1, 단계 0.05로 고정 | 0–1 숫자 | 슬라이더와 dB 표시(`20·log10(v)`, 0이면 "무음") |


지금 변수를 선언한 샘플은 없다.

컴포지션이 변수를 쓰는 규칙.

- `Spot`은 변수 값을 props로 받는다. 상수로 박혀 있던 값을 props 읽기로 바꾼다. `Spot`은 `{...변수 기본값, ...getInputProps(), ...props}`로 합친다. 미리보기는 값을 props로 넘기고 렌더는 `overrides.json`을 입력값(`getInputProps()`)으로 넘기므로 두 경로가 같은 값을 받는다. `calculateMetadata`는 쓰지 않는다.
- 등록 쪽은 `<Composition ... variables={variables} />`로 선언을 넘긴다. 코어의 `Composition`은 `variables` prop을 정의(`CompositionDefinition.variables`)에 그대로 보관만 한다. `defaultProps`를 만들지 않으므로 기본값을 합치는 일은 `Spot`이 한다. frameforge 확장이다. 스튜디오는 `ResolvedComposition.variables`를 `parseVariables`로 읽는다. 서버가 TSX를 해석할 필요가 없다.
- 선언 검사는 코어가 아니라 스튜디오의 `parseVariables`가 한다. `key` 중복, `default`가 타입에 맞지 않음, `number`에 `min`/`max`/`step` 없음, `enum` 선택지가 2개 미만인 항목은 오류를 내지 않고 목록에서 조용히 빠진다. 범위 검사(`valueFits`)는 저장된 `overrides.json` 값에만 적용한다.
- 타이밍 변수는 절대 프레임이 아니라 기획서 장면표 값에 더하는 이동량이다. `Spot`이 장면 순서가 뒤집히지 않게 범위를 정한다. 그 순간의 효과음 `<Sequence from>`도 같은 이동량을 쓴다. 그래야 소리가 화면을 따라간다.
- 문구 변수는 글자 잘림 검사의 대상이다. 긴 문구를 넣으면 무대가 바로 빨간 테두리와 칩으로 알려 준다. 이것이 문구 조정이 안전한 이유다.

### 4.2 덮어쓰기 저장과 적용

`overrides.json`은 폴더에 있고, 기본값과 다른 값만 담은 평평한 객체다.

```json
{"accent": "#F0532F", "pinShift": -6}
```

- 기본값과 같은 값은 저장하지 않는다. 모든 값을 기본으로 되돌리고 저장하면 `{}`를 쓴다.
- 선언되지 않은 키는 지우지 않고 무시하며 조정 탭에 노란 줄로 알린다. 변수 이름이 바뀐 경우 사람이 판단하게 하기 위해서다.
- 타입이 맞지 않는 값(예 `"pinShift": "a"`)은 무시하고 같은 노란 줄로 알린다.

적용 경로는 둘이다.

| 경로 | 방법 | 이유 |
| --- | --- | --- |
| 스튜디오 미리보기 | 무대의 `Scene`이 선택한 컴포지션의 `props`에 그 컴포지션의 덮어쓰기와 초안을 합쳐 컴포넌트에 직접 넘긴다. `setInputProps`와 재탐색은 하지 않는다 | 코어의 입력값은 루트 전체에 하나뿐이다(`setInputProps`, `props = {...defaultProps, ...input}`). 스튜디오 진입 파일(`examples/samples/index.tsx`)은 44개 컴포지션을 등록하므로 입력값으로 넘기면 같은 키를 쓰는 다른 컴포지션에도 들어간다 |
| 렌더 | 서버가 그 폴더의 `overrides.json`을 `renderMedia`의 `inputProps`로 넘긴다 | 렌더 작업 하나는 컴포지션 하나만 그리므로 섞이지 않는다 |

한계. `calculateMetadata`가 props로 길이나 크기를 바꾸는 컴포지션은 미리보기에서 덮어쓰기를 반영하지 못한다(재탐색을 하지 않으므로). 지금 샘플에는 그런 컴포지션이 없다. 생기면 그 컴포지션만 값 변경 시 재탐색하도록 2.1에서 바꾼다.

CLI 렌더(`npm run render -- examples/samples/kit-launch/entry.tsx ...`)는 2.1부터 진입 파일 폴더에 `overrides.json`이 있고 네 번째 인자가 없으면 그 파일을 입력값으로 쓴다(미구현. 지금 CLI는 네 번째 인자의 JSON만 입력값으로 쓴다). 그래야 스튜디오 렌더와 CLI 렌더가 같은 영상을 만든다.

### 4.3 실시간 미리보기 규칙

- 값을 바꾸면(키 입력, 슬라이더 이동, 색 선택) 100 ms 안에 무대가 현재 프레임을 새 값으로 다시 그린다. 측정은 입력 이벤트 시각부터 무대 커밋 뒤 다음 `requestAnimationFrame`까지다. 무대 머리줄의 "반영 N ms"가 이 값이다.
- 지연은 두지 않는다(디바운스 없음). 컴포지션 하나의 한 프레임 그리기는 동기 React 렌더라서 이 예산 안에 든다. 100 ms를 넘은 경우에는 "반영 140 ms"가 노란색이 된다. 문자열 입력을 80 ms 디바운스로 바꾸는 대응은 아직 없다(미구현). 슬라이더는 끄는 동안 계속 그린다.
- 재생 중에 값을 바꾸면 재생을 멈추지 않는다.
- `preview`가 있는 변수에 초점이 가면 무대가 그 프레임으로 간다. 초점이 빠지면 원래 프레임으로 돌아가지 않는다. 사용자가 이어서 그 장면을 볼 가능성이 높아서다.
- `audioVolume` 변수는 미리듣기 음량에도 반영된다. 지금 `syncAudio`가 `clip.volume`을 쓰므로 `<Audio volume>`이 변수를 읽으면 따로 할 일이 없다.
- 초안(저장하지 않은 값)은 컴포지션별로 `localStorage`에 둔다. 새로고침, Vite 재로드, 다른 컴포지션으로의 이동에서 사라지지 않는다.
- 글자 잘림 검사는 값이 바뀔 때마다 다시 돈다(지금 `Stage`의 레이아웃 효과).

저장(⌘S)은 `POST /api/overrides`로 파일을 쓰고, 같은 요청 안에서 `fix` 실행을 덧붙인다. `changes`는 스튜디오가 변수 라벨로 만들고, 서버는 `summary`를 "값 조정 N개"로 쓴다. 예 "강조색 #FF5A36 → #F0532F", "핀 낙하 이동 0 → −6 프레임", "헤드라인 1행 'Too many' → 'So many'". 되돌리기는 초안을 버리고 저장된 값으로 돌아간다.

### 4.4 변경 요청 작성기

과정 탭 아래에 고정된 작성기다. C 키는 어느 탭에서든 과정 탭을 열고 여기에 초점을 준다.

| 요소 | 규칙 |
| --- | --- |
| 프레임 | 기본은 지금 무대 프레임. 오른쪽 "프레임 410 ▾"을 눌러 숫자로 바꾸거나 "프레임 없음"을 고른다 |
| 본문 | 텍스트 영역, 2000자까지. 빈 본문은 보낼 수 없다 |
| 지금 값 첨부 | 저장하지 않은 초안이 있으면 "저장 안 된 값 2개 포함" 체크가 켜진 채로 보인다. 켜면 본문 끝에 "지금 값" 목록이 붙는다. 에이전트가 사용자가 보던 화면을 재현할 수 있게 하기 위해서다 |
| 스틸 첨부 | 2.1. 체크하면 서버가 그 프레임 한 장짜리 시트를 렌더해 `still` 산출물로 붙인다. 지금 렌더러의 시트 경로는 타일을 480 px 폭으로 고정하므로 2.0에서 만들면 480 px다. 2.1에서 `render.mjs`에 타일 폭 옵션을 더해 원래 크기로 만든다 |
| 보내기 | ⌘Enter 또는 버튼. `POST /api/request`. 성공하면 본문을 비우고 목록 맨 위에 "요청 · 열림" 카드가 생기며 타임라인 과정 레인에 마름모가 찍힌다 |
| 실패 | 본문을 지우지 않고 아래에 빨간 한 줄 |

요청은 스튜디오가 에이전트를 실행하지 않는다. 기록만 한다. 에이전트는 3.8절 규약대로 읽고 처리한다. 스튜디오가 에이전트를 직접 띄우는 것은 나중이다.

### 4.5 에디터에서 열기

2.0은 링크만 쓴다. 서버가 `GET /api/project`에서 프로젝트 절대 경로를 알려 주고, 스튜디오가 `vscode://file/<절대 경로>:<줄>:<열>`과 `cursor://file/<절대 경로>:<줄>:<열>`을 만든다. 어느 에디터를 쓸지는 "에디터에서 열기" 펼침 메뉴 아래 "VS Code / Cursor" 선택으로 정하고 `localStorage`에 둔다. 줄 번호를 모르면 `:1:1`이다.

2.1은 `POST /api/open-in-editor`를 더한다. 프로토콜 처리기가 등록되지 않은 컴퓨터에서 서버가 `code -g` 또는 `cursor -g`를 실행한다. 변수에서 열기는 그 변수의 `key` 선언 줄로 간다(서버가 `Spot.tsx`에서 `key: 'pinShift'`를 찾아 줄 번호를 돌려준다).

| 화면 구성 | MP4 렌더 뒤 | `node scripts/frame-check.mjs <mp4> --fps <fps> --json` | `pass`(30프레임 넘는 빈 구간, 120프레임 넘는 정지 구간, 가운데 몰림 비율 0.25 이상, 헤드라인급 요소가 없는 프레임 비율 `thin` 0.08 이상이 모두 없음. 마지막 `hold` 60프레임은 제외) | 줄마다 `fails` 문장. 검사 레인에 `emptyRanges` 회색 빗금, `staticRuns` 노란 띠(60프레임을 넘으면 빨간 테두리. 검사기의 실패 기준은 120프레임이라 테두리가 먼저 보일 수 있다) |
| 음량 | MP4 렌더 뒤, 소리가 있을 때 | `ffmpeg -i <mp4> -af ebur128=peak=true -f null -`의 요약 | I가 `audio.json`의 `loudness.I` ±2 LU 안, TP가 `loudness.TP` 이하. `audio.json`이 없으면 −24 ±2, −2 | "−27.3 LKFS · TP −9.2" 빨간 줄과 [음악 음량 조정] 버튼. 누르면 조정 탭으로 간다 |
| 색 태그 | MP4 렌더 뒤 | `ffprobe -select_streams v:0 -show_entries stream=color_space` | `bt709` | "색 태그 없음. 디코드하면 색이 어두워집니다"(README의 `#06C755` 사례) |

검사는 서버가 렌더 뒤에 순서대로 실행하고 결과를 `check` 실행 하나의 `metrics`에 모은다. 원문 출력은 `<mp4 이름>.checks.json` 로그 산출물로 남긴다. 시트 렌더 뒤에는 글자 잘림만 해당한다(시트 렌더도 `settle()`을 거친다).

기존 샘플은 `renders/samples/results.json`에 검사 결과가 있다. `process.json`에 `check` 실행이 없으면 서버가 이 파일의 해당 항목을 "가져온 결과"로 보여 준다. 이 파일에는 화면 구성 검사가 없어서 그 줄은 "기록 없음"이다. 이 파일은 `renders/` 아래의 로컬 파일이라 저장소에 없고, 그 기계에서 렌더한 작품만 항목이 있다. 항목이 없는 컴포지션(예 `ThreeSpin`)은 "결과 없음"이다.

### 5.2 실패를 드러내는 곳

실패 하나는 네 곳에 동시에 보인다. 한 곳만 보던 사람도 놓치지 않게 하기 위해서다.

1. 레일의 검사 점이 빨강.
2. 출력 탭 결과 카드의 빨간 줄과 이동 버튼.
3. 타임라인 검사 레인의 구간 표시. 누르면 그 구간 시작으로 이동한다.
4. 렌더 실패는 위 막대의 렌더 표시가 빨간 "렌더 실패"로 5초 남는다.

실패는 렌더나 저장을 막지 않는다. 알리고, 원인이 있는 곳으로 데려간다. 결과가 지금 버전보다 오래되었으면 빨강 대신 회색 테두리로 바꾸고 "v2 결과"라고 적는다. 고친 뒤에도 빨강이 남아 사람을 헷갈리게 하지 않기 위해서다.

### 5.3 안전 영역 오버레이

G로 켜고 끈다. 무대 위에 겹치는 선이며 렌더에는 들어가지 않는다.

| 선 | 위치 | 모양 |
| --- | --- | --- |
| 액션 세이프 | 왼쪽과 오른쪽은 폭의 3.5%, 위와 아래는 높이의 3.5% 안쪽(SMPTE 93%) | 점선, 흰색 40% |
| 타이틀 세이프 | 각 변에서 5% 안쪽. `docs/samples/rules.md`의 "가로 5%, 세로 5% 여백" | 실선, 노랑 70% |
| 중심 | 가로세로 중심 십자 24 px | 흰색 40% |

1920×1080에서 타이틀 세이프는 x 96–1824, y 54–1026이다. 1080×1920에서는 x 54–1026, y 96–1824다. 선 바깥에 글자 잉크가 있으면 2.1에서 잘림 칩 옆에 "세이프 밖 1곳" 칩을 더한다(글자 잘림 검사가 이미 잉크 범위를 재므로 같은 값으로 판단한다).

### 5.4 글자 잘림 경고의 위치

지금처럼 잘린 요소에 3 px 빨간 테두리를 그린다. 아래 막대에 문장으로 쓰던 "글자 잘림 N곳: ..."은 무대 머리줄의 칩으로 옮기고, 칩을 누르면 목록 팝오버에서 "퍼즐 · 위 8.3 px"처럼 보인다. 목록 항목에 마우스를 올리면 해당 요소의 테두리가 두꺼워진다. 2.1에서 "모든 프레임 검사" 버튼이 생긴다. 무대가 처음부터 끝까지 프레임을 그리며 잘림을 모으고 검사 레인에 빨간 눈금을 찍는다. 렌더 전에 잘림을 찾는 방법이다.

### 5.5 장면 띠

기획서에서 첫 표를 찾는다. 첫 머리 칸이 "프레임" 또는 "Frames"인 마크다운 표다. 각 행의 첫 칸을 `시작–끝`으로 읽는다. 구분자로 `–`, `-`, `—`를 받는다. 둘째 칸을 띠 이름으로 쓰고 24자에서 자른다. 셋째 칸 이후는 툴팁이다.

- 구간이 겹치면(`tests/fixtures/`의 시험 기획서에 0–150과 126–150이 있다) 겹치는 띠를 둘째 줄에 놓는다. 장면 레인은 최대 두 줄이고 셋째 겹침은 둘째 줄에 덮어쓴다.
- 표를 찾지 못하면 장면 레인에 "기획서에서 장면표를 찾지 못했습니다"를 흐리게 쓴다.
- 띠를 누르면 시작 프레임으로 간다. `[`, `]`는 띠 시작 사이를 오간다.

### 5.6 소리 표시

`audio.json`에서 그린다.

- 구간은 `from`–`to`(초)를 프레임으로 바꾸어 막대로 그린다. 높이는 `energy`에 비례, 라벨은 `label`.
- 히트는 마름모. 마우스를 올리면 "히트 5.0초 (프레임 150)", 누르면 그 프레임으로 간다. `audio.json`의 히트가 `{at, weight, style}` 객체여도 `at`만 읽어 같은 마름모로 그린다. `weight`와 `style`은 소리 생성(`scripts/assets/score.py`)에만 쓰이고 레인에는 보이지 않는다.
- 마지막 2초의 에너지가 0.15를 넘으면 소리 레인 끝에 노란 점과 "규칙 위반 가능. 마지막 2초 에너지 0.5"를 단다(`rules.md`의 소리 규칙).
- 효과음의 실제 위치는 `audio.json`에 없고 `Spot.tsx`의 `<Sequence from>`에 있다. 소리 레인은 효과음을 그리지 않는다(미구현). 스튜디오는 이미 모든 프레임을 정적으로 그려 움직임 파생 효과음을 모으지만(아래) 그때 나오는 `collectAudio()` 결과는 버린다. 이 결과를 모으거나, 렌더가 모은 오디오 구간을 `render` 실행의 `metrics`에 남기면 효과음 눈금을 그릴 수 있다(나중).

미리듣기와 렌더의 소리는 같은 클립 목록에서 나온다. 무대가 그린 프레임의 `<Audio>`와 `<Video>` 클립이 기본이고, `<Video>`는 `playbackRate`(0.25–4)를 반영한다. https 원본 영상은 처음 쓸 때 `.cache/remote/`에 한 번 내려받는다. 여기에 움직임에서 파생된 효과음이 더해진다. 스튜디오는 컴포지션이 바뀔 때마다 모든 프레임을 60프레임씩 나누어 DOM 없이 그려 움직임을 모으고(`App.tsx`), 효과음 맵(`collectSoundMaps()`)을 선언한 컴포지션에서만 `mapSoundEvents(deriveSoundEvents(...))`로 클립을 만든다. 파생 효과음은 시작 프레임부터 3초 창 안에서만 재생하고 좌우 위치(`pan`)를 `StereoPanner`로 적용한다. 효과음이 울리는 동안은 시작 프레임이 0인 음악 클립을 0.6배로 낮춘다. 렌더의 사이드체인 ducking을 흉내 낸 값이다. 렌더(`scripts/render.mjs`)는 같은 파생 효과음을 전체 프레임에서 다시 모아, 직접 넣은 효과음과 0.5초 안에 겹치는 것은 버리고 나머지를 믹스에 더한다. 직접 넣은 효과음이 0.5초보다 가깝거나 4초 안에 4개 이상이면 MP4 렌더는 오류로 멈춘다(시트 렌더에는 적용하지 않는다).

## 6. 시각 디자인

### 6.1 방향

어두운 테마가 기본이고 2.0에는 밝은 테마가 없다. 스튜디오의 색은 거의 무채색이다. 색은 상태(통과, 경고, 실패)와 선택, 초점에만 쓴다. 이유는 컴포지션이 화면에서 가장 색이 많은 것이어야 해서다. 크롬이 색을 쓰면 컴포지션의 색 판단을 흐린다.

### 6.2 색 토큰

기존 `.studio` 토큰 이름(`--background`, `--card`, `--muted-foreground` 등)을 유지하고 값과 몇 개를 더한다.

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `--background` | `oklch(0.16 0 0)` | 앱 바탕 |
| `--panel` | `oklch(0.195 0 0)` | 레일, 검사기, 타임라인 |
| `--card` | `oklch(0.23 0 0)` | 실행 카드, 결과 카드 |
| `--raised` | `oklch(0.27 0 0)` | 마우스 올림, 입력칸 바탕 |
| `--stage` | `oklch(0.25 0 0)` | 무대 바탕. 검정과 흰색 프레임 둘 다 가장자리가 보이는 중간 회색 |
| `--stage-edge` | `oklch(1 0 0 / 14%)` | 프레임 1 px 테두리 |
| `--border` | `oklch(1 0 0 / 9%)` | 구분선 |
| `--foreground` | `oklch(0.96 0 0)` | 본문 |
| `--muted-foreground` | `oklch(0.74 0 0)` | 보조 글자. `--panel` 위 대비 약 7:1 |
| `--subtle-foreground` | `oklch(0.66 0 0)` | 셋째 글자(시각, 경로). `--panel` 위 약 5:1. 이보다 어둡게 쓰지 않는다 |
| `--primary` | `oklch(0.72 0.13 250)` | 선택, 주 버튼, 재생 헤드, 초점 고리 |
| `--primary-foreground` | `oklch(0.18 0.02 250)` | 주 버튼 글자 |
| `--pass` | `oklch(0.76 0.14 155)` | 통과 |
| `--warn` | `oklch(0.82 0.14 85)` | 경고. 규칙 위반 가능, 느린 반영, 모르는 덮어쓰기 키 |
| `--fail` | `oklch(0.70 0.19 22)` | 실패, 글자 잘림(기존 `--destructive`) |
| `--safe-title` | `oklch(0.88 0.16 95 / 70%)` | 타이틀 세이프 선 |

상태 색은 혼자 쓰지 않는다. 언제나 아이콘(`Check`, `TriangleAlert`, `X`)이나 글자와 함께다. 색을 구분하지 못하는 사람도 같은 정보를 받는다.

### 6.3 글꼴과 크기

스튜디오 글꼴은 `public/fonts/line-seed`의 LINE Seed다. 지금 `style.css`의 `@font-face`와 글꼴 순서(`"LINE Seed Sans", "LINE Seed Sans KR", "LINE Seed JP", sans-serif`)를 그대로 쓴다. 굵기는 400과 700만 쓴다. 숫자(프레임, 시간, 수치)는 `font-variant-numeric: tabular-nums`. 경로와 JSON 값은 `ui-monospace` 12 px.

| 단계 | 크기 / 줄 높이 | 굵기 | 쓰는 곳 |
| --- | --- | --- | --- |
| 캡션 | 11 / 16 | 400 | 레인 라벨, 배지, 시각 |
| 작은 본문 | 12 / 18 | 400 | 보조 글자, 경로, 도움말 |
| 본문 | 13 / 20 | 400 | 기본. 입력칸, 목록, 카드 본문 |
| 강조 본문 | 13 / 20 | 700 | 카드 머리, 변수 라벨 |
| 패널 제목 | 14 / 20 | 700 | 탭, 묶음 제목 |
| 화면 제목 | 16 / 24 | 700 | 무대 머리줄 제목 |

### 6.4 간격, 모서리, 밀도

간격은 4 px 단위다. 4, 8, 12, 16, 24, 32만 쓴다. 패널 안쪽 여백 12, 카드 안쪽 12, 카드 사이 8, 묶음 사이 16.

모서리는 `--radius`를 6 px로 낮춘다. 작은 요소(배지, 칩) 4, 입력칸과 버튼 6, 카드 8, 서랍 12. 이전 10 px는 밀도 높은 도구에 둥글었다.

밀도는 "촘촘"이 기본이다. 버튼과 입력칸 높이 28 px, 주 버튼 32 px, 목록 줄 32 px, 패널 머리 36 px, 위 막대 44 px. 클릭 대상은 최소 24×24 px(WCAG 2.2 목표 크기 최소)이고 타임라인 레인 항목은 높이 20 px라도 클릭 영역을 위아래 2 px 넓힌다.

### 6.5 UI의 움직임

움직임은 상태가 바뀌었다는 것을 알리는 데만 쓴다.

| 대상 | 시간 | 곡선 |
| --- | --- | --- |
| 마우스 올림, 누름 색 | 80 ms | ease-out |
| 탭 전환 | 없음. 내용이 바로 바뀐다 | |
| 서랍, 팝오버 열림 | 140 ms, 8 px 미끄러짐 + 투명도 | ease-out |
| 레일 펼침(겹침) | 없음. 바로 펼쳐지고 줄의 마우스 올림 색만 80 ms | |
| 새 실행 카드 등장 | 배경이 `--raised`에서 `--card`로 600 ms. 위치는 움직이지 않는다 | linear |
| 진행 막대 | 값 변경에 120 ms | linear |
| 활성 렌더 카드 | `BorderBeam` 테두리 | |

무대와 컴포지션 주변에는 어떤 UI 움직임도 두지 않는다. 컴포지션의 움직임을 판단하는 자리이기 때문이다. `prefers-reduced-motion: reduce`이면 모든 전이를 0 ms로 하고 `BorderBeam`을 끄고 진행 막대만 남긴다. `MagicCard`는 쓰지 않는다.

### 6.6 접근성

- 대비. 본문과 보조 글자는 바탕 대비 4.5:1 이상, 큰 글자와 아이콘은 3:1 이상. 6.2 표의 값이 기준을 넘는다. `--subtle-foreground`보다 어두운 글자를 만들지 않는다.
- 초점. `:focus-visible`에 2 px `--primary` 고리, 2 px 떨어뜨림. 마우스 클릭에는 보이지 않는다. 무대 본체도 초점을 받을 수 있고(`tabIndex=0`) 초점이 있을 때 ←/→가 동작한다.
- 탭은 `role="tablist"`, `tab`, `tabpanel`과 ←/→ 이동을 갖춘다. 타임라인은 `role="slider"`와 `aria-valuetext="프레임 410, 13.2초, 장면 Focus"`.
- 렌더 진행과 저장 결과는 `role="status"`로 읽히고, 실패는 `role="alert"`.
- 레인 표시(장면, 소리, 검사)는 같은 정보를 검사기에도 글자로 둔다. 타임라인을 볼 수 없는 사람도 검사 실패 구간을 출력 탭에서 읽는다.
- 모든 아이콘 버튼에 `aria-label`. 단축키는 버튼 툴팁에 함께 적는다.

## 7. 서버 API

`vite.config.ts`의 플러그인 목록에 `studioApi`(`src/studio/server/studioApi.ts`)가 있고, 이 미들웨어가 `/api` 아래를 맡는다. 옛 `studioSave`와 `/api/save`는 없다. 응답은 모두 `application/json; charset=utf-8`이고 오류는 `{fault: 한국어 문장, detail?: 원문}`이다. `readBody`는 본문을 10 KB(10000바이트)까지 받는다. 요청 본문 2000자, 덮어쓰기, 프레임 40개는 이 안에 들어간다.

### 7.1 공통 보안 규칙

| 규칙 | 내용 |
| --- | --- |
| 루프백만 | 서버는 지금처럼 `127.0.0.1`에만 묶는다. 미들웨어는 `req.socket.remoteAddress`가 `127.0.0.1`, `::1`, `::ffff:127.0.0.1`이 아니면 403. `Host` 머리는 `paths.ts`의 `ownOrigin`처럼 루프백 이름(`127.0.0.1`, `localhost`, `[::1]`)만 받는다(DNS 리바인딩 방지) |
| 다른 사이트의 요청 막기 | 같은 컴퓨터의 아무 웹 페이지나 `127.0.0.1:4317`로 POST를 보낼 수 있다. 그래서 모든 POST는 `Origin` 머리가 서버 자신의 origin과 같아야 하고 `content-type`이 `application/json`이어야 한다. 아니면 403. 모든 `GET`(SSE 포함)도 `Origin`이 있으면 같은지 본다. `Origin`이 없는 `GET`은 통과한다 |
| 경로 제한 | 받은 경로를 프로젝트 루트 기준으로 풀고 `realpath`로 실제 경로를 얻은 뒤, 그 경로가 `realpath(프로젝트 루트) + 경로 구분자`로 시작해야 한다. 문자열 앞부분 비교만으로는 심볼릭 링크로 빠져나갈 수 있어서 `realpath`가 필수다. 절대 경로 입력, NUL 문자, `node_modules/`, `.git/`, 점으로 시작하는 파일(`.env` 등)은 거절. 예외로 `.scratch/` 아래는 읽기를 허용한다(에이전트 프롬프트와 로그가 거기 있다) |
| 셸 없음 | 외부 프로그램은 `spawn(명령, 인자 배열)`로만 실행하고 `shell: true`를 쓰지 않는다. 사용자 입력은 인자 배열의 한 원소로만 들어간다 |
| 컴포지션 ID | `^[A-Za-z][A-Za-z0-9-]*$`(`paths.ts`의 `COMPOSITION_ID`)이고 `GET /api/project`가 아는 ID여야 한다. 경로는 ID에서 서버가 만든다. 클라이언트가 출력 경로를 정하지 않는다 |

### 7.2 엔드포인트

| 메서드와 경로 | 요청 | 응답 | 오류 |
| --- | --- | --- | --- |
| `GET /api/project` | 없음 | 아래 7.3 | 500 진입 파일을 읽지 못함 |
| `GET /api/file?path=` | `path` 프로젝트 루트 기준 | `{path, text, mtime}` | 400 경로 형식, 403 루트 밖 또는 금지 경로, 404 없음, 413 1 MB 초과, 415 허용하지 않는 확장자 |
| `GET /api/media?path=` | 같음 | 파일 바이트, `Range` 지원(206) | 위와 같음. 범위가 틀리면 416 |
| `POST /api/overrides` | `{compositionId, values, changes}` | `{overrides, run}` | 400 ID 형식 오류, 모르는 컴포지션, 값이 평평한 객체가 아님(값은 문자열, 유한한 숫자, 불리언), 404 폴더 없음 |
| `POST /api/request` | `{compositionId, text, frame}` | `{run}` | 400 빈 본문, 2000자 초과, 프레임 범위 밖 |
| `POST /api/render` | `{compositionId, kind: 'mp4' 또는 'sheet', frames?}` | `{jobId, position}` (`position` 0이면 바로 시작) | 400 `sheet`인데 프레임이 1–40개가 아니거나 범위 밖 정수 |
| `GET /api/render` | 없음 | `{jobs}` (7.3의 `jobs`와 같은 모양) | |
| `GET /api/render/:id/events` | 없음 | SSE. 7.4 | 404 모르는 작업 |
| `POST /api/open-in-editor` (2.1) | `{path, line?, editor: 'vscode' 또는 'cursor'}` | `{ok: true}` | 404 파일 없음, 500 `code`나 `cursor` 명령 없음 |

`GET /api/file` 허용 확장자는 `.md`, `.json`, `.tsx`, `.ts`, `.mjs`, `.txt`, `.log`. `GET /api/media` 허용 확장자와 형식은 `.png` `image/png`, `.mp4` `video/mp4`, `.wav` `audio/wav`.

`POST /api/overrides`는 서버가 임시 파일에 쓰고 이름을 바꿔 `overrides.json`을 원자적으로 쓴다(이 파일에는 잠금이 없다). 이어서 `scripts/process.mjs`의 `append`로 `fix` 실행(actor `human`)을 덧붙인다. 잠금은 `append` 안에만 있어서 두 쓰기 사이에 서버가 멈추면 값은 저장되고 실행 기록이 빠질 수 있다. 이때 응답은 200에 `fault`를 담아 알린다. 변수 선언은 서버가 모르므로 타입 검사는 스튜디오가 하고, 서버는 모양(평평한 객체, 원시 값, 키 형식 `^[a-zA-Z][a-zA-Z0-9]*$`, 키 64개 이하)만 본다. 바뀐 것이 없으면(저장된 값과 같으면) 파일도 실행도 쓰지 않고 그대로 돌려준다. 같은 요청을 두 번 보내도 결과가 같다.

`POST /api/render`의 출력 경로는 서버가 정한다. `renders/studio/<폴더 경로의 마지막 이름 또는 소문자 ID>/<YYYYMMDD-HHMMSS>-v<N>.<mp4|png>`. 폴더가 없는 컴포지션도 렌더할 수 있고, 이때는 `process.json`에 기록하지 않는다. 작업마다 `127.0.0.1:4318`에 `hmr: false`인 Vite를 하나 더 띄워 `scripts/render.mjs`의 `renderMedia`를 부르고, 그 폴더의 `overrides.json`을 `inputProps`로 넘긴다. CLI 렌더가 같은 포트를 쓰고 있으면 렌더는 "렌더 포트 4318을 다른 렌더가 쓰고 있습니다"로 실패한다.

### 7.3 `GET /api/project` 응답

```json
{
  "root": "/path/to/frameforge",
  "entry": "examples/samples/index.tsx",
  "compositions": [
    {
      "id": "KitLaunch",
      "folder": "examples/samples/kit-launch",
      "title": "kit-launch",
      "files": {"spot": "examples/samples/kit-launch/Spot.tsx", "brief": "examples/samples/kit-launch/prompt.md", "audio": "examples/samples/kit-launch/audio.json", "process": null, "overrides": null},
      "brief": "# kit-launch\n...",
      "audio": {"value": {"slug": "kit-launch", "bpm": 120}},
      "process": {"value": null},
      "overrides": {"value": {}},
      "importedResults": {"flash": {"pass": true, "worstSecondTransitions": 2}, "loudness": {"I": -24.94, "TP": -9.22, "LRA": 10.4}, "colorSpace": "bt709"}
    }
  ],
  "jobs": []
}
```

- `jobs`는 서버 메모리의 렌더 작업 목록이다. 스튜디오는 새로고침 뒤 진행 중인 작업에 다시 붙는 데 쓴다.
- 컴포지션과 폴더의 연결은 진입 파일 어디에도 적혀 있지 않다. 서버가 만든다. 진입 파일이 있는 폴더의 하위 폴더를 훑어 `<하위 폴더>/entry.tsx`를 읽고 `<Composition>`, `<Still>` 태그의 `id`, `fps`, `durationInFrames`를 정규식으로 뽑는다(`fps`와 길이는 요청 프레임 범위 검사와 렌더 총 프레임 수에 쓴다). 뽑은 ID가 그 하위 폴더의 컴포지션이다. 진입 파일 자신이 폴더 안의 `entry.tsx`이면 그 폴더다. 연결되지 않은 ID는 `folder: null`(예 `src/demo-entry.tsx`의 컴포지션).
- 컴포지션 목록과 순서, 길이, 크기는 스튜디오가 이미 브라우저에서 탐색한 값을 쓴다. 서버 응답은 ID로 합친다. 그래서 진입 파일에 등록되지 않은 폴더(예 `examples/samples/_template/`)는 목록에 나오지 않는다.
- 파일 하나가 깨져도 응답 전체가 실패하지 않는다. JSON 파일은 `{value}` 또는 `{error: "3번째 줄 14열: ..."}`로 온다.
- `importedResults`는 `process.json`에 `check` 실행이 없을 때만 `renders/samples/results.json`에서 슬러그로 찾아 넣는다.

### 7.4 렌더 이벤트(SSE)

`text/event-stream`. 연결하면 서버가 먼저 지금 상태 하나를 `snapshot`으로 보낸다. 작업이 이미 끝났으면 `snapshot` 뒤에 마지막 `done`이나 `failed`를 한 번 더 보낸다. 그래서 다시 연결해도 같은 화면이 된다.

| event | data | 언제 |
| --- | --- | --- |
| `snapshot` | `{state, kind, compositionId, position, rendered, total, stage, startedAt, log}` (`log`는 마지막 20줄) | 연결 직후, 작업이 시작될 때 |
| `queued` | `{position}` | 대기열 순서가 바뀔 때 |
| `stage` | `{stage}`. `audio`, `frames`, `encoding`, `checks` 중 하나 | 단계가 바뀔 때. `audio`는 소리 생성이 필요할 때만 |
| `progress` | `{rendered, total}` | 프레임마다. 서버는 최대 초당 10번으로 묶어 보낸다 |
| `check` | `{name, pass, summary}` | 검사 하나가 끝날 때 |
| `done` | `{artifact: {kind, path, frames?}, runId, checkRunId?}` | 끝 |
| `failed` | `{fault, detail, frame?}` | 실패. 글자 잘림이면 `frame`을 채운다 |
| `log` | `{line}` | 렌더러와 검사의 표준 출력, 오류 출력 한 줄 |

작업은 서버 메모리에만 있다. 서버를 다시 켜면 진행 중이던 작업은 사라지고 이벤트 연결은 404를 받는다. 스튜디오는 이를 2.8절의 "서버 재시작으로 작업 사라짐"으로 보여 준다. 끝난 작업은 10분 동안 이벤트 재연결에 응답한 뒤 버린다. 기록은 `process.json`에 남아 있다.

### 7.5 파일 변경 알림

에이전트가 `process.json`, `overrides.json`, `prompt.md`, `audio.json`을 바꾸면 스튜디오가 알아야 한다. 새 연결을 만들지 않고 Vite가 이미 가진 것을 쓴다. 서버는 `server.watcher`에서 이 네 이름의 변경을 보고 `server.ws.send({type: 'custom', event: 'frameforge:project', data: {folder}})`를 보낸다. 스튜디오는 `import.meta.hot.on('frameforge:project')`에서 `GET /api/project`를 다시 읽는다. `Spot.tsx` 변경은 지금처럼 Vite가 처리하고, 2.10절의 해시가 위치를 지킨다.

## 8. 수용 기준

### 8.1 브라우저에서 확인하는 목록

준비. `VIDEO_ENTRY=examples/samples/index.tsx npm run dev` 후 Chrome에서 `http://127.0.0.1:4317`. 진입 파일의 컴포지션 아홉 개 중 변수를 선언한 것과 `process.json`이 있는 것은 지금 없다. 과정과 조정 항목은 `node scripts/process.mjs init <폴더>`로 `process.json`을 만들거나 변수를 선언한 작품를 먼저 만든 뒤에 본다.

배치

- [ ] 창 1920×1080. 레일 248 px, 검사기 400 px, 타임라인 208 px. KitLaunch 무대가 1195×672 px 근처(±4 px)이고 가로 스크롤이 없다.
- [ ] 창 1280×800(브라우저 안쪽 약 1280×700). 레일이 64 px로 접히고, 16:9 무대 폭이 780 px 이상이며, 가로 스크롤이 없다.
- [ ] 창 1100 px. 검사기가 서랍이 되고 I로 열고 닫힌다.
- [ ] 레일에 제목이 `prompt.md` 첫 제목으로 보인다. `main.tsx`에 `SCENE_TITLES`가 없다.

탐색과 단축키

- [ ] Space, ←, →, Shift+→(10프레임), Home, End가 동작한다. 프레임 410에서 시간이 `0:13:20`(13 × 30 + 20 = 410)으로 보인다.
- [ ] 입력칸에 글자를 치는 동안 Space가 재생을 시작하지 않는다. 입력칸에서 ⌘S는 저장한다.
- [ ] 1–4로 탭이 바뀐다. 탭은 Tab 키로 들어가 ←/→로 이동하며 초점 고리가 보인다.
- [ ] 주소가 `#/KitLaunch@410`이 되고, 새로고침하면 같은 컴포지션의 410 프레임이 열린다.

과정

- [ ] `process.json`이 있는 작품의 과정 탭에 작성, 리뷰, 수정 실행이 최신 순으로 있고 수정 카드에 "바뀐 것" 줄과 버전 배지가 있다. 버전 번호가 author와 fix 실행 수와 같다.
- [ ] 시트가 있는 실행을 누르면 타임라인 과정 레인에 시트 프레임 수만큼 눈금이 찍힌다. 눈금 위에 마우스를 올린 미리보기 타일이 그 프레임의 무대 화면과 같은 장면이다(3.5절 식 확인).
- [ ] 시트 보기에서 각 타일 왼쪽 위에 프레임 번호가 있고, 타일을 누르면 무대가 그 프레임으로 간다.
- [ ] 리뷰 실행의 지적 옆에 해결한 버전이 보인다.
- [ ] 프레임 668에서 C, 문장 입력, ⌘Enter. 목록 맨 위에 "요청 · 열림 · 프레임 668"이 생기고, 그 폴더의 `process.json` 끝에 `kind: "request"`, `frame: 668` 실행이 있다. 과정 레인 668에 마름모가 있다.
- [ ] 터미널에서 `node scripts/process.mjs append examples/samples/kit-launch '{"actor":"claude opus","kind":"fix","summary":"밑줄 시점 조정","resolves":["<요청 id>"]}'`를 실행하면, 새로고침 없이 2초 안에 과정 탭에 새 수정 카드가 생기고 요청이 "해결 v<N>"으로 바뀐다.

조정

- [ ] 변수를 선언한 작품의 조정 탭에 선언한 변수가 묶음별로 있다(위 예는 9개).
- [ ] "헤드라인 1행" 입력칸에 초점을 주면 무대가 프레임 40으로 간다. 글자를 바꾸면 무대 머리줄의 "반영 N ms"가 100 이하로 보인다. 열 번 바꿔 열 번 모두 100 이하.
- [ ] 헤드라인 1행에 "Too many unfinished"를 넣으면 잘림 칩이 빨강이 되고 해당 글자에 빨간 테두리가 생긴다(또는 잘리지 않으면 칩이 회색 그대로다. 둘 중 무엇이든 칩과 테두리가 일치한다).
- [ ] 강조색을 바꾸고 ⌘S. `overrides.json`에 기본값과 다른 키만 있고, 과정 탭에 actor "사람"의 수정 카드가 "강조색 #FF5A36 → ..."로 생긴다. 같은 값으로 한 번 더 ⌘S를 눌러도 실행이 늘지 않는다.
- [ ] 저장하지 않고 다른 컴포지션으로 갔다 돌아오면 초안이 남아 있고, 레일에 저장 안 됨 점이 보인다.
- [ ] KineticTypo 조정 탭은 "변수를 선언하지 않았습니다" 빈 상태다.
- [ ] `음악 음량`을 0으로 하고 재생하면 음악이 들리지 않고 효과음은 들린다.

출력과 검사

- [ ] KitLaunch 출력 탭의 시트 프레임 칩이 기획서 검사 프레임 개수만큼 채워져 있다. 시트 만들기를 누르면 진행 카드가 프레임 수를 세고, 끝나면 결과 카드에 번호가 겹쳐진 시트가 보인다. 파일이 `renders/studio/kit-launch/` 아래 새 이름으로 생기고 기존 `renders/samples/kit-launch-sheet.png`는 그대로다.
- [ ] MP4 만들기. 진행 카드의 프레임 수가 1초에 여러 번 오르고, 마지막 프레임 뒤 "인코딩", 그 뒤 "검사"가 보인다. 결과 카드에 검사 다섯 줄(글자 잘림, 플래시, 화면 구성, 음량, 색 태그)이 있고 `<video>`가 재생된다. 음량 줄의 I 값이 `ffmpeg -af ebur128`을 손으로 돌린 값과 같다.
- [ ] 렌더 도중 페이지를 새로고침하면 진행 카드가 같은 진행률로 돌아온다.

## 9. 구현 지시

### 9.1 먼저 지킬 것

`render.mjs`가 의존하는 렌더 모드 다리는 바꾸지 않는다. `?render` 쿼리, `window.__FRAMEFORGE_INPUT__`, `window.__FRAMEFORGE_ERROR__`, `window.__FRAMEFORGE__`의 `compositions`, `configure`, `renderFrame`, `audit`, `audio`, `video`, `artifacts`, `soundClips`, 그리고 `settle()`의 대기 순서와 글자 잘림 실패. 모듈을 나누는 첫 커밋에서 이 부분은 옮기기만 하고 고치지 않는다. 그 커밋이 끝나면 8.1절 회귀의 시트 렌더를 돌린다.

### 9.4 순서

2.0 범위의 구현은 끝났고, 아래는 구현 때의 순서를 남긴 것이다. `tests/studio.test.tsx`는 장면표, 검사 프레임, 버전과 해결 계산, 덮어쓰기, `sfxFault`, `playbackBlocker`를 시험한다. 2단계의 잠금 중 동시 덧붙이기와 깨진 JSON 시험은 아직 없다(미구현).

각 단계는 확인 하나로 끝난다. 확인이 통과해야 다음으로 간다.

1. 빼기. `SCENE_TITLES`, `/api/save`, `studioSave`, 위 막대의 "영상 저장" 버튼, 아래 막대의 잘림 문장을 지운다. `main.tsx`에서 `runtime.tsx`를 떼어 낸다. 확인. `npm test`, 시트 렌더 회귀, 지금 스튜디오가 재생된다.
2. 모델과 기록. `model.ts` 타입과 파서, 버전 계산, `scripts/process.mjs`. 확인. 테스트 파일 하나로 잠금 중 동시 덧붙이기 두 개가 둘 다 남는지, 깨진 JSON에 덧붙이기가 실패하고 파일을 건드리지 않는지 본다.
3. 서버 읽기. `studioApi`의 `project`, `file`, `media`와 `paths.ts`. 확인. 8.1절 보안 curl 다섯 개.
4. 배치. `App`, `Rail`, `StageView`, `Timeline`의 전송 줄과 눈금자, 크기 규칙, 해시, 단축키. 확인. 8.1절 배치와 탐색 항목.
5. 기획과 레인. `brief.ts`, 기획 탭, 장면 레인, 소리 레인. 확인. 겹치는 장면 띠가 두 줄로 보이고 `0-150` 형식도 읽힌다.
6. 과정. 과정 탭, 시트 보기, 과정 레인, 요청 작성기, `POST /api/request`, 파일 변경 알림. 확인. 8.1절 과정 항목.
7. 조정. 코어 `variables`, 변수를 쓰는 작품 하나를 props로 바꾸기, 조정 탭, `POST /api/overrides`. 확인. 8.1절 조정 항목, 그리고 그 작품의 기본값 시트가 바꾸기 전 시트와 같은 화면이다(기본값이 원래 상수와 같아야 하므로).
8. 출력. `jobs.ts`, `checks.ts`, SSE, 출력 탭, 검사 레인, 결과 카드. 확인. 8.1절 출력 항목.
9. 다듬기. 2.8절 상태 표를 한 줄씩 만들어 본다. 동작 줄이기, 초점 고리, 대비. 확인. 8.1절 전체.

하루를 넘기면 8.2절 끝의 자르기 순서를 따른다.
