# 샘플 영상 제작 규칙

샘플 제작의 기본 지침이다. 사용자의 명시적 요청이 우선하며, 진단 수치와 창작 판단은 구분한다.

## 파일

- `examples/samples/<slug>/Spot.tsx`: 컴포지션. `useCurrentFrame()`은 루트에서 한 번. 장면 컴포넌트는 `frame`을 props로 받는다. 예외는 `<CameraMotionBlur>` 하나다. 블러의 복사본은 정지된 하위 트리라서, 그 안의 그림 루트에서 한 번 더 불러 소수 프레임을 받는다(`examples/samples/morph-ui/Spot.tsx`의 `Picture`).
- `examples/samples/<slug>/entry.tsx`: 이 컴포지션 하나만 `registerRoot`로 등록. 장면 ID는 PascalCase slug.
- `examples/samples/<slug>/audio.json`: 소리 사양(아래 소리 절). `assets.json`(그림 에셋 해결 사양)과 `assets.tsx`(직접 그린 에셋)는 필요할 때만.
- `examples/samples/<slug>/brief.md`: 엔진 브리프. 기획보다 먼저 쓴다(아래 "기획 구조"의 0번). 템플릿은 `examples/samples/_template/brief.md`.
- `examples/samples/<slug>/prompt.md`: 기획. 아래 "기획 구조" 절의 칸(입력, 방향, 구조, 빌드, 두 번째 패스, 함정, 시작)을 채운다. 템플릿은 `examples/samples/_template/prompt.md`.

## 기획 구조

장면표만 있는 기획은 "무엇을"만 정하고 "어떤 취향으로"를 비워 둔다. 그 빈칸을 모델이 채우면 헤드라인과 카드를 컷으로 잇는 평범한 영상이 나온다. 잘 만든 모션 그래픽 프롬프트는 거의 모두 아래 칸들로 되어 있어서, `prompt.md`도 이 순서를 따른다. 그 앞에 요청을 옮기는 엔진 브리프가 온다.

0. **엔진 브리프(`brief.md`).** 사용자 요청을 그대로 두고 엔진에 맞게 옮긴다. 의도는 하나도 잃지 않는다. `## Request`에 요청 원문을 고치지 않고 붙인다. `## Intent ledger`는 요청의 절마다 한 행이다. 행은 따옴표로 그대로 옮긴 절, 종류(`must` 필수, `forbid` 금지, `taste` 취향, `implied` 장르가 당연히 기대하는 것. 예: 쇼릴의 이름 카드, 런칭의 제품 공개), 엔진 수단(셰이더 프리셋, 블록, 이음새, `audio.json` 필드, 크기·fps·길이), 확인 위치(구조 행과 프레임 범위, 또는 검사 이름)를 적는다. 절들을 합치면 요청의 모든 단어가 들어가야 한다. `## Engine translation`은 엔진 말로 다시 쓴 기획(컨셉, 세계, 주인공, 팔레트, `showreel.md` 계열과 대표 기법, 길이·크기·fps, 소리)이다. 구체성은 더해도 되지만 필수와 금지를 거스르거나 약하게 하거나 빼지 않는다. 취향은 필수와 부딪히지 않으면 지킨다. implied는 명시된 절을 이기지 못한다. "마음대로" 같은 열린 요청은 과감하게 정하고 `Decision:`으로 적어 사용자의 의도와 구별한다. `## Gaps`에는 엔진이 못 하는 것이나 서로 부딪히는 것과 고른 대안을 적는다(없으면 `None.`). 조용히 빼지 않고, 마지막 보고에서 사용자에게 다시 말한다. `node bin/frameforge.mjs brief-check <slug>`의 실제 결과와 해결하지 못한 충돌을 기록한다. 대체된 과거 요구를 오인한 FAIL도 숨기지 않는다. `brief.md`가 없는 작품은 이 단계 전에 만든 것으로 보고 SKIP한다. `frameforge new`와 템플릿 복사는 늘 `brief.md`를 가져오므로 새 작품은 채울 때까지 FAIL이다.
1. **입력.** 시작 전에 정해야 할 것. 상태 목록, 색, 곡의 BPM, 가상 브랜드 이름. 사용자에게 받을 것과 기본값을 적는다.
2. **방향.** 한 문단으로 쓰는 취향. 기준이 되는 수준, 주인공 하나, 카메라가 하는 일, 글꼴, 이징 성격을 적는다. 끝에 `금지:` 한 줄을 둔다. 금지에는 이 작품이 빠지기 쉬운 상투를 이름으로 적는다("헤드라인 + 카드 세 장 나열", "페이드로만 등장", "템플릿처럼 보이는 것", "빈 박자").
3. **구조.** 각 사건의 절대 프레임 범위, 이전·이후 상태, 시선과 읽기 시간을 적는다. 음악이 편집을 이끌면 BPM과 마디별 사건을 함께 적는다. 실제 컷은 `Cuts: none` 또는 `Cuts: 120, 300`으로 기록하며 seam-check는 이 줄을 읽는다.
4. **빌드.** fps, 렌더링 층, 에셋 출처·권리, 타이포, 움직임·카메라 곡선과 소리 배치를 정한다. 애니메이션 전에 대표 장면을 실제 소재·서체·조명으로 만들고 원본과 전달 크기에서 표정, 형태 깊이, 시선, 보상 조건과 글자 가림을 점검한다. 허용된 관찰 수단이 없으면 관찰하지 못했다고 기록한다.
4b. **비평과 수정.** 허용된 방법으로 저장된 결과의 사건 전·중·후와 읽기 구간을 관찰한다. 우선순위가 높은 구체적 결함을 고치고 같은 구간을 다시 확인한다. 예를 들어 보상 조건이 270px 폭에서 작다면 글자를 키우고 같은 저장 프레임을 비교한다. 정해진 장면 수나 새 기법을 채우지 않으며 결과와 한계를 `prompt.md`에 적는다.
5. **함정.** 이 종류의 영상에서 실제로 깨지는 것과 피하는 법. 만들면서 겪은 것을 추가한다.
6. **시작.** 승인된 범위 안에서 상태 목록과 대표 장면을 스스로 만들고 점검한다. 사용자가 이미 자율 진행을 요청했다면 별도 확인을 기다리지 않는다.

기존 칸(목적, 가상 브랜드, 형식, 색, 글꼴, 크기, 소리, 검사 프레임)은 입력과 빌드 안에 둔다.

## 결정성

- 모든 값은 프레임 번호의 함수. `Math.random`, `Date`, `performance.now`, state, effect, CSS transition/animation 금지. 난수는 `random('seed')`, 이어지는 난수열은 `rng('seed')`. 캔버스와 셰이더도 프레임마다 처음부터 그린다(그리기 사이에 상태를 남기지 않는다).
- 같은 프레임을 두 번 그리면 같은 화면.

## 화면

- 크기·길이·fps는 요청과 전달 매체에 맞춘다. 1920×1080 또는 1080×1920, 30fps는 예시이며 빠른 움직임이나 모션 블러는 필요할 때 더 높은 fps를 택한다. 검사 도구는 실제 fps를 읽는다.
- 팔레트의 색 수는 컨셉과 소재에 맞춰 선택한다. 작은 화면의 대비와 압축 후 색을 확인하며, 제한된 색은 선택지이지 필수 기준이 아니다.
- 모션그래픽은 `skills/frameforge-motion/SKILL.md`에 따라 사건의 상태, 시각적 중심과 읽기 시간을 설계한다. 정지나 컷은 의도에 맞으면 허용하며, 렌더 기법과 매체는 요청에 맞게 고른다.
- 블록, 모티프 키트와 셰이더 프리셋은 요청에 맞을 때 사용할 수 있다. 예제의 구성이나 모양을 그대로 복사하는 대신 작품의 컨셉에 맞게 선택한다.
- 컨셉이 먼저다. Structure 표 앞에 `Concept:` 문단 하나. 하나의 아이디어, 그것이 일어나는 세계, 다시 나오며 상태가 바뀌는 주인공 하나, 컨셉에서 나온 팔레트(기본값 아님), 대표 기법과 그것을 만드는 코드, 모션이 글의 뜻을 어떻게 행동하는지. 장면 목록을 다른 요청의 영상에 그대로 붙여 넣을 수 있으면 다시 시작한다. 저장소의 문서와 예제에 있는 장면, 팔레트, 문구는 가져다 쓰지 않는다.
- 모서리 수치(타임코드, 프레임 카운터, 장면 번호, BPM, REC)는 기본으로 쓰지 않는다. 렌더 감사가 영상의 절반 넘게 모서리에 남는 작은 글자를 `corner_hud`로 잡는다. 컨셉이 정말 카메라나 방송이면 `data-hud="allow"`와 이유를 적는다.
- 전환과 마지막 화면은 요청과 읽기 시간에 맞게 설계한다. frame-check의 `featureless`와 마지막 2초 motion share 결과는 실제 상태를 보고하고, 의도된 홀드와 충돌하면 그 이유를 명시한다.
- 얼굴, 캐릭터, 보석, 사진, 질감과 효과는 브리프와 사용 권한에 맞으면 사용할 수 있다. 클립아트나 광택·파티클을 무작정 추가하지 말고 형태와 시선을 돕는지 확인한다. 효과가 주요 글자를 가리지 않도록 저장 결과에서 검토한다.
- 서체는 요청과 권리에 맞춰 고른다. 재현성을 위해 허가된 로컬 글꼴을 우선할 수 있으며, Google Fonts는 외부 접근이 허용된 경우에만 사용한다. `googleFont`는 모듈 맨 위에서 부르고 캔버스의 `ctx.font`에도 같은 가족을 쓴다. 시스템 대체 글꼴의 환경별 차이는 보고한다.
- 글자 크기와 안전 여백은 전달 매체와 읽기 시간에 맞춰 정한다. 짧은 변의 헤드라인 10%, 라벨 3.5%, 여백 5%는 진단 출발점이며 모든 장르의 미적 합격선은 아니다.
- 글자 마스크는 블록의 `blockMask`(위 0.1em, 아래 0.4em, 좌우 0.3em 여유, `examples/samples/explainer-patterns`의 `Glyphs`도 같은 것을 쓴다). 글자 잉크가 마스크나 프레임 밖으로 나가면 렌더가 `Clipped text` 오류로 멈춘다. 일부러 넘치는 띠에는 `data-clip="allow"`.
- 실제 회사·제품·로고나 수치를 요청받으면 제공되거나 사용 권한이 있는 자료를 쓰고 출처·권리를 기록한다. 가상 브랜드와 예시 수치는 가상임을 명시한다.
- 샘플 수치는 작품의 언어로, 작게, 한 번 표기한다. 통계마다 태그를 다는 대신 그 박에 각주 하나를 둔다. 영어 작품은 "Sample data", 일본어는 "サンプルデータ", 한국어는 "샘플 데이터"나 "예시". 블록의 `example`은 `true | false | '글자'`이고, 글자를 주지 않으면 `lang` 또는 블록 글자의 문자 체계에 따라 Sample, サンプル, 예시를 고른다. 태그를 맡은 블록 하나만 남기고 나머지는 `example={false}`로 끈다.

## 구성과 진단

아래 숫자는 도구의 진단과 샘플의 출발점이다. 크기나 화면 점유율만으로 완성도를 판정하지 말고, 저장된 대표 장면을 원본과 실제 전달 크기에서 확인한다.

- 글자를 한 자씩 `inline-block`으로 분해해 올릴 때 공백은 `'\u00A0'` 이스케이프로 넣는다(템플릿의 보이지 않는 NBSP 리터럴은 베껴 쓰다 보통 공백으로 바뀌어 사라졌다). 보통 공백만 든 inline-block은 너비 0으로 접혀 "아침,어디서시작하죠?"처럼 띄어쓰기가 사라진다(cafe-morning 초판에서 발생).
- 진단 예: 짧은 변의 헤드라인 10%, 라벨 3.5%, 아이콘 6%, 주인공 35%, 여백 5%. 내용과 매체에 맞게 조정하고 가독성과 가림을 직접 확인한다.
- 첫 화면의 시선과 정보는 브리프에 맞게 설계한다. 큰 이미지가 유효할 수 있지만 의도된 여백이나 작은 피사체를 일률적으로 금지하지 않는다.
- 각 장면에서 관객이 무엇을 먼저 보고 무엇을 이해해야 하는지 적는다. 여백이나 배경만 있는 순간도 의도와 맥락으로 판단한다.
- `npm run frame-check -- renders/samples/<slug>.mp4`의 실제 결과를 보고하고 각 경고·실패 구간을 의도와 대조한다. 마지막 1초(끝 정지, `--hold`로 변경)는 기본 측정에서 빠진다. 도구 기준:
  - 빈 화면 없음. 배경색이 아닌 픽셀이 1% 미만인 프레임이 1초 넘게 이어지면 실패.
  - 작은 요소만 있는 화면 8% 미만. 잉크가 가로의 5% 이상 지나는 행이 짧은 변의 6% 높이만큼 연속하지 않는 프레임(헤드라인급 요소가 없는 프레임)의 비율.
  - 가운데 몰림 25% 미만. 잉크 상자가 가로 40% 미만이면서 세로 40% 미만인 프레임의 비율.
  - 얼어붙은 구간 1초 이하. 0.5초 전 프레임과 비교해 바뀐 픽셀이 0.2% 미만인 프레임은 얼어 있다. 그런 구간이 1초를 넘으면 실패한다. 초당 몇 px의 카메라 드리프트도 움직임으로 잡힌다(헤드라인이 있는 화면에서 1 px/s부터 잡혔다). `motion share`(움직이는 프레임 비율)와 옛 정지 지표(바로 앞 프레임과 비교한 `static`, `still share`)는 참고로 출력한다.
- 픽셀 면적(배경이 아닌 비율)은 참고로만 출력한다. 잘 만든 샘플도 중앙값이 3–4%라서 기준으로 쓰지 않는다. 기준값은 `renders/samples`의 열네 편으로 맞췄다(opus 샘플은 통과, 작은 요소와 빈 화면이 지적된 샘플은 실패).

## 에셋과 아이콘

- 주인공과 보조 자산은 직접 그린 벡터, 허가된 래스터·3D·키트 등 목적에 맞는 방법으로 만든다. 출처와 권리를 기록하고, 외부 서비스·유료 도구는 승인된 경우에만 사용한다. 키트나 해결기는 선택지이며 기본 품질을 보장하지 않는다.
- 대표 에셋을 실제 장면에 넣어 원본과 전달 크기에서 실루엣, 표정·포즈, 재질과 조명, 깊이, 색 대비, 다른 정보와의 가림을 확인한다. 필요하면 에셋 시트를 쓰되 모양 개수나 단일 선 굵기를 품질 기준으로 강제하지 않는다.
- 아이콘이나 라이브러리는 권리와 작품의 시각 언어가 맞을 때 쓴다. 출처·라이선스를 기록하고 범용 자산이 주인공을 대체해 정보를 약화시키지 않는지 검토한다.
- SVG는 적절한 `viewBox`와 프레임 함수로 구동한다. 선이 그려지는 효과가 목적에 맞으면 `pathLength={1}`, `strokeDasharray={1}`, `strokeDashoffset={1 - draw}`를 쓸 수 있다. 형태 수·채움·등장 방식은 소재와 연출에 맞춘다.
- 크기와 세부 밀도는 실제 전달 크기에서 확인한다. 실제 브랜드 자산과 유료 자료는 사용 권한과 비용 승인이 있을 때만 사용한다.

## 모션

- 연결 방식은 요청과 리듬에 맞춰 고르고 혼합할 수 있다. 다음은 가능한 두 예다.
  - **연속 모핑.** 주인공 하나가 끊기지 않고 상태를 바꾼다(버튼 → 로더 → 체크 → 카드 → 차트). 크기, 모서리, 색과 안의 내용을 바꾸며 사건의 관계를 전달할 수 있다. 모핑 자체가 인과나 완성도를 보장하지는 않으므로 전환을 직접 살핀다.
  - **장면 잇기.** 장면을 컷으로 잇는다. 모든 컷은 seam이다(`references/seams.md`).
- 카메라는 구도와 시선을 설계하는 수단이다. 필요할 때 줌·이동을 사용하고 `<MotionProbe family="camera" axis="x|y|scale">`로 기록할 수 있다. 변화 방향은 장면의 목적에 맞춘다.
- 움직임의 곡선은 대상과 감정에 맞춰 스프링, 이징, 프레임별 선형·비선형 함수 중 고른다. `springTrack`은 여러 목표를 프레임의 순수 함수로 연결하는 한 방법이다. 오버슈트와 타이밍은 실제 결과를 보고 판단한다.
- 커서가 변화를 일으키면 실제 클릭과 드래그처럼 보이게 한다. 클릭은 눌림(scale 0.9)과 놓임, 드래그 중 값은 커서 위치에서 계산한다.
- 빠른 움직임에 블러가 필요할 때 `<CameraMotionBlur shutterAngle={180} samples={4}>`를 쓸 수 있다. 블러 안의 `MotionProbe`와 `Audio`는 보고되지 않으므로 프로브와 소리는 블러 바깥에 둔다.
- 변화와 홀드의 길이는 음향·서사·읽기 시간에 맞춘다. 페이드, 컷, 연속 움직임 모두 의도에 맞으면 쓸 수 있다.
- 과정 영상의 변화가 관객에게 무엇을 알려 주는지 살핀다. 카메라 재구성이나 누적 표시를 쓸 수 있고, 같은 레이아웃을 유지하는 편이 이해에 도움되는 경우도 있다.
- 과정 영상의 소품은 의미와 사용 맥락이 알아보이도록 표현한다. 직접 그린 물체, 적절한 아이콘, 권리 있는 이미지나 3D를 고를 수 있다. 예를 들어 병은 기울어 자기 목에서 붓게 만들 수 있다(`Bottle`과 `bottleNeck`).
- 보조 움직임은 시선과 감정에 도움이 될 때만 쓴다. 읽기 홀드나 정적 엔딩도 의도에 맞으면 유지하고, 진단을 통과하려고 드리프트를 추가하지 않는다.
- 과정(레시피, 작동 원리, 조립, 데이터 흐름)을 보여 줄 때는 원인과 결과를 같은 화면에 동시에 보인다. 붓는 줄기와 차오르는 수위, 물건을 나르는 화살표. 줄기와 흐름은 `<Stream from to progress width color wobble>`으로 그린다. 붓기의 첫 프레임부터 줄기가 보이는 동안 수위와 수량 숫자가 함께 바뀐다. 줄기가 보이는데 수량이 0에 머물지 않는다. 주인공은 프레임 안에 온전히 두고, 수량 라벨은 물체 위에 붙인다(눈금, oz, %). 주인공 요소에 `data-subject="이름"`을 달면 렌더 감사가 프레임 밖으로 2% 넘게 나간 주인공을 `element_cropped`로, 글자를 20% 넘게 가린 주인공을 `subject_overlaps_text`로 잡는다. 물체에 붙은 라벨은 그 `data-subject` 요소 안에 두면 가림으로 세지 않는다. 일부러 프레임 밖에서 들어오는 주인공에는 `data-clip="allow"`.
- 글자 등장 방식은 정보의 읽기 시점과 장르에 맞춰 고른다. `GlyphRise`, `Typewriter`, `ZoomSwap`이나 다른 프레임 함수를 쓸 수 있으며, 중간 상태가 의도한 의미와 가독성을 해치지 않는지 저장 프레임에서 확인한다.
- 헤드라인과 엔딩에는 필요한 읽기 시간을 확보한다. 정적 록업, 움직이는 록업, 루프 모두 의도에 맞으면 가능하다. 루프 검사에는 `frame-check --hold 0`을 쓴다.
- 컷과 플래시는 리듬과 전달 맥락에 맞게 설계하고 `flash-check`의 실제 결과를 확인한다. 임의의 횟수 제한만으로 안전이나 미적 품질을 보장하지 않는다.
- 카메라가 확대하는 요소에 `will-change`를 두지 않는다. 글자가 흐려진다. 모핑하는 상자 안에서 바뀌는 글자는 나가는 글자와 들어오는 글자에 따로 타이밍을 준다. 같이 두면 겹친다.

## 소리

- 사용 권한이 있는 음원이나 작품의 로컬 음원을 쓴다. 엔진 샘플의 `audio.json` 생성 결과는 `public/audio/generated/<slug>/`에 남는다. 외부 프로젝트는 공용 생성 오디오의 충돌을 막기 위해 자동 score·voice 생성과 공용 생성 오디오 읽기가 임시 차단되므로, 명시적으로 준비한 프로젝트 로컬 음원이나 스냅샷을 사용한다.
- 소리의 섹션과 타격을 장면의 의도에 맞게 설계한다. `hits`를 화면 사건과 연결할 수 있지만, 조용한 도입이나 강한 엔딩도 브리프에 맞으면 가능하다.
- 엔진 샘플의 생성 음악은 `<Audio src="/audio/generated/<slug>/music.wav" volume={0.9} />`로 연결할 수 있다. 외부 프로젝트의 명시적 로컬 음원은 프로젝트 `public/` 안의 경로로 연결한다.
- 효과음은 사양의 `sfx[]`에 `name`과 `intent`(무슨 소리인지 한 문장)와 `length`로 적는다. 생성기가 CC0 라이브러리 → 합성 순으로 소스를 정하고 `sfx.json`에 고정한다(`docs/audio-score.md` 효과음 절). 프리셋 이름만 적는 옛 방식은 폴백이다.
- 움직임에 맞는 효과음은 `useMotionSound`/`<MotionProbe>`와 `<MotionSound role>`로 유도하거나, 의도에 따라 `<Sequence><Audio/></Sequence>`로 직접 배치한다. 실제 동기화 판단에는 청취가 필요하다.
- 효과음의 밀도와 음량은 사건과 믹스에 맞춘다. 렌더러의 간격·밀도 검사는 실제 제한이므로 오류를 보고하고 필요하면 연출을 조정한다.
- 음악의 섹션과 리듬은 의도에 맞춘다. 한 박짜리 섹션의 잦은 교체는 연결이 어색할 수 있으므로 사용 가능한 경우 최종 믹스를 듣고 판단한다.

## 검사

- 허용된 방법으로 중요한 사건 전·중·후, 대표 구도와 마지막 프레임을 관찰한다. 프레임 수를 채우는 대신 확인 구간과 미관찰 구간을 기록한다.
- `node bin/frameforge.mjs brief-check <slug>`와 `frameforge check --film <slug>`의 실제 결과를 보고한다. 의도 장부를 관찰과 대조해 각 필수·금지 절의 충족, 실패, 미검증을 구분한다.
- `npm run build`와 `npm test`가 통과해야 한다. `npm run lint:video -- examples/samples/<slug>/entry.tsx`에 `error`가 없어야 한다.
- 요청 범위를 렌더한 뒤 `npm run frame-check`와 `node scripts/flash-check.mjs`의 실제 결과를 기록한다. 전체 렌더는 허용된 범위에서만 하며 동시 실행 시 `FRAMEFORGE_PORT`를 별도로 지정한다.
